## Per-subtopic findings, tagged by sourcing confidence

**1. ElizaOS itself**

- 🟢 Core facts: MIT-licensed TypeScript framework, grew out of the ai16z DAO (launched Oct 2024 by Shaw Walters), rebranded to ElizaOS Jan 28 2025 after a16z asked it to stop using a confusing name — a16z never invested in it. `AgentRuntime` core with a plugin system registering **actions** (do things), **providers** (feed context), and **evaluators** (post-process into memory) — directly confirmed against docs.elizaos.ai.
- 🟢 Real, verified chain plugins (checked live against npm/GitHub): `@elizaos/plugin-evm` (any viem-compatible EVM chain, config-driven — includes a documented custom-RPC pattern), `@elizaos/plugin-solana`, `@elizaos/plugin-aptos` (narrower than claimed — token transfer + balance monitoring, **not** PTB execution), `@elizaos/plugin-sui` (package real, versioned through 1.0.1; detailed feature claims unverified — repo fetch 404s), `@elizaos/plugin-goat`.
- 🟠🔴 **Corrections to the seed notes**: no `@elizaos/plugin-iota` exists at all — the claimed IOTA support has no primary evidence. "GOAT (Gastoken Open Agent Toolkit)" was a hallucinated name; the real project is **GOAT = "Great Onchain Agent Toolkit"** (Crossmint-originated), and its upstream SDK repo is now **archived/unmaintained** — a caveat the seed notes missed. "Aptos PTB execution" is wrong; PTBs are Sui-specific, Aptos uses Move entry functions/scripts instead — likely a conflation from the Sui plugin description bleeding into the Aptos one.
- 🟡 Payments/treasury: wallet/signing is handled per-chain-plugin, not by one unified core wallet API. No primary evidence of native x402 or ERC-8004 support — a third-party facilitator ("AsterPay") claims ERC-8004-readiness with ElizaOS plugin support, but that's single-source, promotional in tone. `plugin-tee` and `plugin-lit` point toward scoped/hardened key isolation conceptually adjacent to the chapter's session-key protocols, but no source ties them to those EIPs by name.
- 🟢🔴 **Most important finding**: ElizaOS/ai16z effectively **collapsed as an organization in 2026**. A federal class-action (*Doe v. Walters*, SDNY, filed April 2026) alleged the "autonomous" AI fund was actually human-operated, that a16z's identity was appropriated, and that a Nov 2025 token migration diluted holders via a 40% supply expansion to fund insider/SAFT allocations — with no functioning on-chain DAO vote ever having shipped despite the "DAO" branding. Founder Shaw Walters settled in August 2026, declared the $ELIZAOS token "dead," and wound the foundation down — corroborated across 6+ independent outlets plus the law firm's own case page. The open-source `elizaOS/eliza` codebase (MIT, ~19.3k GitHub stars as of 2026-09-08) reportedly continues under Walters as IP owner, independent of any DAO/token.
- 🟢 Separately, a May 2025 Princeton/Sentient Foundation study found ElizaOS agents vulnerable to **"memory injection"**: an attacker plants false memories (e.g. coordinated fake social posts) that the agent later trusts as history, capable of hijacking privileged actions like token transfers — a concrete illustration that an agent's internal memory, not just on-chain settlement, is a security-critical trust boundary.
- 🟡 No evidence of anyone using ElizaOS (or any comparable framework) for the SDLC-automation pattern this chapter centers on — adoption evidence skews entirely to crypto-trading/social-media agents.

**2. Other comparable open-source frameworks**

- 🟢 **GAME (Virtuals Protocol)** — real, MIT-licensed Python/Node SDKs, Agent/Worker/Function primitives (structurally analogous to ElizaOS's action model). On-chain wallet/signing lives at the Virtuals platform layer and a separate **Agent Commerce Protocol (ACP)**, not in the open SDK itself. Much smaller GitHub footprint than ElizaOS (93 stars on game-node vs ~19.3k), but tied to a still-operating token/platform, unlike ElizaOS's collapsed one.
- 🟢 **Rig / rig-onchain-kit / riglr** (Rust) — Rig is a general-purpose LLM framework with reported production users (Neon, St Jude, Nethermind, Coral Protocol); `rig-onchain-kit` and the separate `riglr` project add Solana/EVM chain interaction. riglr's notable feature: a `SignerContext` pattern that explicitly isolates private-key material from the LLM's reasoning loop — a named architectural answer to "keep the LLM away from key material." riglr itself is tiny (7 stars) — early-stage.
- 🟡 **open-autonomy (Olas/Valory)** — real, Apache-2.0, confirmed via direct fetch (127 stars). Architecturally a **different category** from the other three: a multi-agent, Tendermint-consensus **service** framework (a quorum of redundant agents reaching internal consensus before an on-chain commit), not a single-agent-plus-tool-plugins framework. Should not be described with the same "plugin = LLM tool" language as ElizaOS/GAME/Rig.
- GOAT/goat-sdk is a cross-framework tool library (plugs into ElizaOS, LangChain, others), not itself a full agent framework — noted as shared infrastructure, now unmaintained upstream.

**3. Common architectural pattern**

- 🟢 All three single-agent frameworks (ElizaOS, GAME, Rig/riglr) share the same shape: a core LLM perceive→reason→act→remember loop, with blockchain capability added as a pluggable "tool" layer (action / Function / `#[tool]`-macro'd function) rather than built into the core — "give this agent the ability to transfer a token" is always a bolt-on unit, never a special-cased core feature.
- 🟢 Chain operations are exposed to the LLM as callable tools structurally analogous to — and in two cases directly interoperable with — **MCP**: Rig has native MCP support; ElizaOS has a community plugin bridging out to MCP servers plus an open core-repo issue tracking native support. No MCP integration found for GAME or open-autonomy.
- 🟢 Key-isolation sophistication varies but recurs as a theme: ElizaOS's opt-in `plugin-tee`/`plugin-lit`, riglr's `SignerContext`, GAME's wallet-at-platform-layer — all application-layer analogues of the protocol-layer problem the chapter's session-key standards (EIP-7702/ERC-4337/ERC-7715) already address: keep the token-prediction process away from direct key control.
- 🟢 Multi-chain support is always chain-scoped plugins/crates, never one universal wallet API — a real technical constraint (SVM account model vs. Move object/resource models aren't unifiable behind one interface), not a framework-design gap.
- 🟡 open-autonomy is the explicit outlier and shouldn't be folded into this pattern.

**4. Evidence quality**

- Several "build a crypto AI agent with ElizaOS + [vendor]" blog posts (Gelato, Ankr, QuickNode, MetaMask) are vendor content marketing their own product through a tutorial — useful to confirm an integration exists, but not a disinterested technical assessment.
- Numeric claims to hold loosely: ElizaOS's "90 official / 200+ total plugins" figure, contributor-count figures (1,350 total / 583→355 active), Rig's "7,600+ stars" — all single-source, not independently re-verified via direct fetch in this pass.

## Named-entity corrections flagged by the research agent

- "GOAT (Gastoken Open Agent Toolkit)" → **"GOAT (Great Onchain Agent Toolkit)"**, Crossmint-originated, upstream repo now archived.
- "Aptos PTB execution" via ElizaOS's Aptos plugin → not supported by any source; PTBs are Sui-specific. The Aptos plugin does token transfer + wallet/balance monitoring only.
- `@elizaos/plugin-iota` → does not exist; no primary evidence of any IOTA-specific ElizaOS integration (the closest evidenced path is the generic `plugin-evm` reaching IOTA EVM by configuration, which is plausible-by-mechanism but not directly documented).

## What this means for the book (suggestion, not a decision)

The chapter currently has zero coverage of the agent-framework layer — it jumps straight from "why a public DLT" to "which network" to "which payment/identity protocol," skipping over what a developer actually writes code against. Suggest adding a new `### Open-source agent frameworks` subsection under "Public DLTs for Agentic Fabrics," after "Which DLT network to use," roughly covering:

1. A short intro framing the gap: protocols (already covered) are what an agent *speaks*; a framework like ElizaOS is what a developer actually *builds with* to make an agent speak them.
2. ElizaOS as the leading example — architecture (action/provider/evaluator plugin model), real chain support (with the corrections above baked in, not the seed notes' errors), and its tie-in (or lack thereof) to the chapter's existing protocol stack.
3. A pointed **Research Note** on the 2026 lawsuit/wind-down — this is load-bearing for the book's own "when is a public DLT the right engineering choice" skepticism already established earlier in the chapter (the TradeLens-style "solution in search of a problem" discussion): ElizaOS is a case where the *token/DAO* layer collapsed under exactly the kind of governance-in-name-only critique the chapter already primes readers to be skeptical of, while the underlying *open-source framework* layer is unaffected and continues. Worth explicitly distinguishing "is ElizaOS-the-framework worth using" from "was ai16z-the-DAO a sound governance model" — conflating them would be a mistake in either direction.
4. A brief comparison table or paragraph covering GAME, Rig/riglr, and open-autonomy — enough to establish the recurring "LLM loop + pluggable chain-action tool layer" pattern (and riglr's `SignerContext` as a nice concrete tie-back to the chapter's session-key material), with open-autonomy flagged as the consensus-based outlier.
5. The Princeton memory-injection finding fits naturally as a second Research Note under a security/limitations angle — it's a good concrete complement to the chapter's existing "agents as cryptographic keypairs" framing: the keypair can be well-protected by EIP-7702 scoping and still be walked into an unauthorized transfer via a corrupted memory store, which is a distinct attack surface from anything the protocol stack addresses.
6. Explicitly note the adoption gap: no evidence any of these frameworks are actually used for SDLC/software-factory automation today — this is consistent with, and should be stated alongside, the chapter's existing "composition is coherent but currently hypothetical" line about the tokenized-build-artifact and on-chain/off-chain orchestration ideas.
