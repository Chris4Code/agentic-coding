# Open-Source DLT-Native Agent Frameworks: ElizaOS and Comparable Projects

Research pass conducted 2026-09-08. This note fills the "agent framework" layer gap in the DLT software-factories chapter — the actual open-source software developers use to build a crypto-native agent, as distinct from the underlying protocols (x402, ERC-8004, EIP-7702/4337/7715, MPP, AP2, DID/VC, zkTLS) which the chapter already covers.

## 1. ElizaOS itself

### What it is and origin

ElizaOS is an open-source, TypeScript-first framework for building autonomous AI agents, described by its own repository as "Your agentic operating system" ([GitHub: elizaOS/eliza](https://github.com/elizaOS/eliza)). It is MIT-licensed.

The project's origin is well corroborated across independent secondary sources: it grew out of **ai16z**, a decentralized autonomous organization (DAO) launched in October 2024 by developer Shaw Walters, originally pitched as a lighthearted, "playful reference" to venture firm Andreessen Horowitz (a16z) while raising roughly $75,000 to build an autonomous AI-managed investment fund on Solana ([Unchained: ai16z rebrands to ElizaOS](https://unchainedcrypto.com/ai16z-is-rebranding-as-elizaos-after-request-from-venture-firm-a16z/), [CryptoManiaks: What Is ElizaOS](https://cryptomaniaks.com/guides/what-is-elizaos-ai-16z)). On January 28, 2025, the project rebranded from "ai16z" to "ElizaOS" after Andreessen Horowitz's own crypto arm asked the project to stop using a name that was causing confusion with the VC firm; a16z's Chris Dixon stated a16z was "not connected with AI16z" and had not invested in it ([Unchained](https://unchainedcrypto.com/ai16z-is-rebranding-as-elizaos-after-request-from-venture-firm-a16z/), [Cryptopolitan](https://www.cryptopolitan.com/ai16z-rebrands-to-elizaos-confusion-concerns/)).

**Research Note:** the seed research chat's framing of ElizaOS as simply "a major standard for building crypto-native AI agents" understates a significant, well-corroborated organizational collapse that happened very recently relative to this research date (2026-09-08). See "Known limitations, criticisms, controversies" below — this is not a minor footnote, it materially changes how "current governing organization" should be described.

**Current governing organization / foundation:** as of this research date, there effectively is none in the DAO/foundation-treasury sense the project originally advertised. Following a federal class-action lawsuit (*Doe v. Walters*, filed in the U.S. District Court for the Southern District of New York, case 1:26-cv-03238, filed April 20–22, 2026), founder Shaw Walters announced on August 4, 2026 that the Eliza Labs/ai16z foundation was winding down, declared the $ELIZAOS token "dead," ruled out any future token, buyback, or foundation support, and stated the framework's software development would continue independently under him as the IP owner, outside of any DAO/foundation structure ([Yahoo Finance/CryptoRank: ElizaOS Token Collapses as Foundation Shuts Down](https://finance.yahoo.com/markets/crypto/articles/elizaos-token-collapses-time-low-053048980.html), [CryptoRank](https://cryptorank.io/news/feed/872a8-eliza-token-shut-down-as-founder-winds-down-foundation-following-legal-settlement), [crypto.news](https://crypto.news/eliza-token-declared-dead-as-founder-winds-down-foundation-after-legal-settlement/), [Own Your Mind review](https://ownyourmind.ai/projects/elizaos/)). The open-source `elizaOS/eliza` codebase itself remains published and MIT-licensed and, per the same coverage, active development continues — this is a governance/treasury/legal collapse of the DAO and its token, not (yet, as of this research date) an abandonment of the code repository.

### Architecture: plugin system

Primary-sourced from ElizaOS's own documentation ([docs.elizaos.ai/plugin-registry/overview](https://docs.elizaos.ai/plugin-registry/overview)): the runtime is organized around a central `AgentRuntime` (defined in the `@elizaos/core` package) that acts as the orchestrator for agent lifecycle, plugin loading, and message handling. A plugin is an object implementing a `Plugin` interface that can register:

- **Actions** — discrete tasks the agent can perform, each with its own validation logic (can this action run given current context?) and execution logic (what it actually does, e.g. transferring a token).
- **Providers** — supply real-time contextual data to the agent (e.g. current wallet balance, market price) so the LLM's reasoning step has up-to-date external state.
- **Evaluators** — post-process conversation/interaction data to extract insights and build the agent's long-term memory.
- Additionally, per the same source, plugins can register services, model handlers, HTTP routes, event hooks, tests, and app views — a broader extension surface than just the three core primitives.

This action/provider/evaluator triad is the mechanism through which a blockchain plugin adds "the ability to sign and submit a transaction" (an action), "the current balance/gas price" (a provider), and "did this trade look profitable in hindsight" (an evaluator) to an otherwise chain-agnostic conversational agent loop.

### Chain support — verified against primary sources

The seed research's specific package claims were checked directly against the npm registry and GitHub. Findings:

- **`@elizaos/plugin-evm`** — real and confirmed. Provides token transfers, cross-chain bridging, and token swaps via LiFi integration across "EVM-compatible chains" generically ([npm](https://www.npmjs.com/package/@elizaos/plugin-evm), [GitHub: elizaos-plugins/plugin-evm](https://github.com/elizaos-plugins/plugin-evm)). Chain selection is configured in the agent's character config (`settings.chains.evm: ["base","arbitrum","optimism",...]`), with names matched against `viem/chains`, and a custom RPC URL can be supplied per chain via an environment variable pattern (e.g. `ETHEREUM_PROVIDER_<CHAIN_NAME>=<rpc-url>`) — a documented example shows this pattern used for IoTeX, a non-default chain, confirming the plugin is not hardcoded to a fixed chain allowlist. This directly supports the seed claim that IOTA EVM (a viem-compatible chain) could be reached this way, though no source explicitly documents an IOTA EVM (chain ID 8822) example the way IoTeX is documented — **this specific claim is plausible-by-mechanism but not directly evidenced**, so treat "IOTA EVM support via plugin-evm" as inferred, not confirmed.
- **`@elizaos/plugin-solana`** — real, confirmed via npm. Described as a "core Solana blockchain plugin" providing token operations, trading, portfolio management and DeFi integration services ([npm](https://www.npmjs.com/package/@elizaos/plugin-solana)).

### Agent-to-agent payments, treasury, and wallet management

ElizaOS's own plugin layer (plugin-evm, plugin-solana, plugin-aptos, plugin-sui, plugin-goat) gives an agent the mechanical ability to hold a keypair and sign/submit transactions, i.e., the wallet/treasury layer is handled per-chain by these plugins rather than by a single unified wallet abstraction in `@elizaos/core`.

Concrete tie-ins to the identity/payment protocol stack already in the book chapter (x402, ERC-8004):

- A third-party payments infrastructure provider ("AsterPay," described as a European x402 facilitator) advertises itself as "ERC-8004 ready with ElizaOS plugin support" ([search synthesis, no further primary confirmation obtained]) — **single-source, promotional in tone, not independently corroborated**. Treat as a claim that an ElizaOS-x402/ERC-8004 integration exists via a third-party facilitator, not as evidence of first-party ElizaOS/Eliza-Labs support for these protocols.
- No primary ElizaOS documentation or blog post explicitly describing native x402 or ERC-8004 support was found in this research pass. This is a gap: the framework-level plugin architecture (actions/providers) is clearly *capable* of wrapping x402 or ERC-8004 calls (any HTTP/RPC-callable protocol can become a plugin action), but no evidence was found that Eliza Labs itself has shipped or documented such a plugin as of this research date.
- Separately, `@elizaos/plugin-tee` (trusted execution environment) and `@elizaos/plugin-lit` (Lit Protocol threshold/programmable key management) point toward the general pattern of scoped, non-human-custodied signing authority conceptually adjacent to session-key protocols like EIP-7702/ERC-4337/ERC-7715 already covered in the chapter, though no source found ties these plugins explicitly to those specific EIPs by name.

The seed notes' closing claim — that ElizaOS lets "one agent scrape, another verify logic, another audit security, paying each other directly in crypto for compute or data" — was not found stated this specifically by any primary or secondary source in this research pass. It reads as a plausible extrapolation from the framework's general action/plugin capabilities (an agent *could* be scripted this way using existing wallet-plugin actions) rather than a documented, named ElizaOS feature or reference deployment. **Treat as speculative/illustrative, not an evidenced ElizaOS capability or case study.**

### Known limitations, criticisms, and controversies

This is the most substantively new — and most negative — finding of this research pass relative to the seed notes' framing, and is well corroborated across many independent outlets:

1. **Federal class-action lawsuit (Doe v. Walters, SDNY, filed April 20–22, 2026).** Plaintiffs allege false advertising, deceptive practices, negligent misrepresentation, and unjust enrichment. Specific allegations, per the law firm's own case page and multiple news outlets: the project was marketed as governed by an autonomous AI agent but was allegedly "human-operated, not autonomous as advertised" (the "Marc AIndreessen" agent persona specifically named); the ai16z brand allegedly appropriated Andreessen Horowitz's identity without authorization; a November 2025 token migration expanded total token supply by 40% (from 6.6B to 11B tokens) without a working on-chain community vote, diluting original holders from notionally 100% to 60% of supply to fund SAFT-investor (15%), team (10%), foundation (4.5%), and ecosystem (2.5%) allocations; and there was alleged insider selling ahead of announcements ([Burwick Law case page](https://www.burwick.law/active-cases/ai16z-elizaos-token-lawsuit-doe-v-walters), [KuCoin news](https://www.kucoin.com/news/flash/ai16z-and-elizaos-creators-face-federal-lawsuit-over-alleged-fraud-and-market-manipulation), [Own Your Mind review](https://ownyourmind.ai/projects/elizaos/)). The complaint reportedly identifies roughly 3,945 wallet addresses as having sustained losses, with the token having fallen from an all-time-high market cap over $2.6B (January 2, 2025) to roughly $0.00055/token, a >99.9% decline ([claimdepot.com case summary](https://www.claimdepot.com/cases/ai16z-class-action-alleges-founders-faked-ai-agent-misled-investors-in-26b-crypto-scheme), [Own Your Mind](https://ownyourmind.ai/projects/elizaos/)).
2. **Settlement and wind-down (announced August 4, 2026).** Founder Shaw Walters stated the foundation lacked the capital to litigate — quoted as saying the claims were "ridiculous, but we didn't have the capital to legally fight it" — and chose to settle by distributing the remaining treasury to token holders, declare the token "dead," rule out any buyback or future token, and wind down the foundation ([Own Your Mind](https://ownyourmind.ai/projects/elizaos/), [crypto.news](https://crypto.news/eliza-token-declared-dead-as-founder-winds-down-foundation-after-legal-settlement/), [solanafloor.com](https://solanafloor.com/news/the-token-is-dead-eliza-labs-founder-pulls-the-plug-on-ai-16-z-after-treasury-settlement)). Software development is stated to continue independently under Walters as IP owner, decoupled from any token/DAO ([Yahoo Finance/CryptoRank](https://finance.yahoo.com/markets/crypto/articles/elizaos-token-collapses-time-low-053048980.html)).
3. **Governance-in-name-only critique.** Independent review states ElizaOS/ai16z never had functioning on-chain voting despite its "DAO" branding, and that major decisions (the rebrand, the 40% supply expansion, SAFT allocations) were made unilaterally by project leadership; a promised DAO voting module reportedly never shipped ([Own Your Mind](https://ownyourmind.ai/projects/elizaos/)).
4. **Security research: memory-injection vulnerability (disclosed ~May 2025).** Independent of the governance/legal issues, Princeton University researchers (led by graduate student Atharv Patlan, with Sentient Foundation) published a technical finding that ElizaOS agents managing crypto assets are vulnerable to "memory injection" attacks: because the framework's persistent memory store has no integrity verification, an attacker can plant false "memories" (e.g. via coordinated fake social-media posts — a Sybil attack) that the agent later treats as trusted historical context, up to hijacking privileged actions like `transfer()` into sending funds to an attacker. This bypasses surface-level prompt-injection defenses because the exploited trust boundary is the memory layer, not the immediate prompt. The findings were shared with Eliza Labs; Eliza Labs' response (per the same coverage) emphasized rapid iteration and being one of the few open-source AI companies submitting to peer review, and some partial fixes were reportedly rolled out, but the researchers characterized the security model for persistent-memory LLM agents generally as still immature ([Decrypt](https://decrypt.co/318200/elizaos-vulnerability-ai-gaslit-losing-millions), [2-spyware.com](https://www.2-spyware.com/crypto-at-risk-prompt-injection-flaws-in-elizaos-revealed)). This finding is directly relevant to the book chapter's "tamper-evident provenance trail" framing: it is a concrete illustration that an agent's *internal* state (memory), not just the on-chain settlement layer, is a security-critical trust boundary for a paid autonomous agent.

## 2. Other comparable open-source frameworks

### GAME by Virtuals Protocol

Real and comparable. GAME ("Generative Autonomous Multimodal Entities," per secondary sources) is the agentic decision-making framework underpinning **Virtuals Protocol**, a platform on Base (an Ethereum L2) plus, more recently, Ethereum mainnet and (from March 2026) Arbitrum, for creating tokenized/co-owned AI agents ([Virtuals docs](https://docs.game.virtuals.io/), [search synthesis on Virtuals multi-chain expansion]). It is open-source with a Python SDK and a Node/TypeScript SDK, both MIT-licensed ([GitHub: game-by-virtuals/game-python](https://github.com/game-by-virtuals/game-python), [GitHub: game-by-virtuals/game-node](https://github.com/game-by-virtuals/game-node), confirmed MIT license and 93 stars on game-node as of 2026-09-08). Architecturally it is built around three primitives — **Agent, Worker, and Function** — where an Agent plans, Workers group related capabilities, and Functions are the concrete callable actions, structurally analogous to ElizaOS's action model though with different naming. Unlike ElizaOS's core repo, the `game-node` SDK's own README contains no blockchain/wallet code directly; on-chain wallet and transaction-signing capability is provided at the Virtuals Protocol platform layer (an "on-chain wallet operator" component letting agents hold assets, sign transactions and earn fees) and via a separate **Agent Commerce Protocol (ACP)** for agent-to-agent verifiable transactions, rather than being built into the open-source GAME SDK itself ([search synthesis on Virtuals/GAME architecture and ACP] — **this Agent/Worker/Function-vs-wallet-layer split is inferred from combining the SDK README fetch and secondary Virtuals-ecosystem descriptions, not from one single primary source describing the full stack end-to-end; treat the precise division of responsibility as corroborated-secondary, not primary-confirmed**).

Compared to ElizaOS: narrower star count/community size by the numbers found in this pass (93 stars on game-node vs. ~19.3k on elizaOS/eliza — not a fully apples-to-apples comparison since GAME's ecosystem activity may concentrate on a different repo or off-GitHub, but directionally GAME reads as smaller/newer as an open developer community), but tied to a live, still-operating token/platform (Virtuals/$VIRTUAL) at the time of this research, in contrast to ElizaOS's collapsed token. GAME's agent-commerce story is more explicitly "agents transact with each other for services" from the outset (via ACP) than ElizaOS's more general-purpose plugin model.

### Rig / rig-onchain-kit / riglr (Rust ecosystem)

Real and comparable, though structured as a layered stack rather than one project:

- **Rig** (`rig-core`) is a general-purpose, MIT-licensed Rust framework (not blockchain-specific by itself) for building LLM-powered applications — completions, embeddings, RAG, vector stores — across 20+ model providers, with MCP support and reported production users including Neon, St Jude, Nethermind, and Coral Protocol ([GitHub: 0xPlaygrounds/rig](https://github.com/0xPlaygrounds/rig); star figure of "7,600+" cited by a secondary blog post is **single-source and unverified against a direct repo fetch in this pass**).
- **rig-onchain-kit**, built by the same org (0xPlaygrounds) in partnership with "listen," is the companion crate that adds Solana/EVM blockchain interaction on top of Rig's core LLM-to-tool pipeline ([GitHub: 0xPlaygrounds/rig-onchain-kit](https://github.com/0xPlaygrounds/rig-onchain-kit)).
- **riglr** is a separate, MIT-licensed project built on top of Rig, adding "enterprise-grade infrastructure, security patterns, and blockchain-specific tooling" — real-time on-chain event streaming, multi-chain support (Solana and EVM chains as primary targets, with new chains addable "with a single environment variable" per its own README), and a notable architectural feature: a `SignerContext` pattern that keeps private keys/signing isolated from the LLM's reasoning loop, plus a `#[tool]` macro to reduce boilerplate when exposing a Rust function as an agent-callable tool ([GitHub: riglr/riglr](https://github.com/riglr/riglr), directly fetched 2026-09-08: 7 stars — this is a small, early-stage project, much smaller than ElizaOS or GAME by star count).

Compared to ElizaOS: same general shape (LLM agent loop + pluggable chain-actions-as-tools layer) but in Rust instead of TypeScript, explicitly prioritizing signing-key isolation from the LLM (`SignerContext`) as a named architectural safeguard — relevant to this book's "agents as cryptographic keypairs" framing, since it is a concrete answer to "how do you stop the LLM's own reasoning from directly touching private key material."

### Olas / Autonolas — "open-autonomy" (distinct from the Olas network/protocol)

Real, but a materially different kind of framework than ElizaOS/GAME/Rig, and worth flagging as such rather than treating as a drop-in comparable. `open-autonomy`, maintained by Valory under the `valory-xyz` GitHub org, is Apache-2.0 licensed and describes itself as "a framework for the creation of autonomous agent services": off-chain multi-agent systems (MAS) that reach internal consensus (built on Tendermint, per its dependency list) before committing outcomes on-chain, explicitly aimed at letting a decentralized group of agent operators jointly execute logic "arbitrarily complex" beyond what a smart contract alone can do, with the multi-agent consensus step providing the trust-minimization ([GitHub: valory-xyz/open-autonomy](https://github.com/valory-xyz/open-autonomy), directly fetched 2026-09-08: 127 stars, Apache-2.0, requires Python ≥3.10, uses Tendermint for consensus and IPFS for distributed storage).

This is architecturally distinct from ElizaOS/GAME/Rig's "one LLM-driven agent with a plugin/tool layer" shape: open-autonomy's unit of trust is a *quorum of redundant agent instances agreeing*, not a single agent's tool-calling loop. It is a genuine, real, open-source codebase (not just the Olas token/protocol already in the chapter), so it belongs in this section, but it should be presented as a different architectural niche — decentralized *service* consensus — rather than as another ElizaOS-style single-agent framework.

### Other named projects encountered but not deep-dived

- **GOAT / goat-sdk** (see Section 1) functions as a cross-framework tool library rather than a full agent framework (it plugs into ElizaOS, LangChain, and others rather than providing its own agent loop) — noted here because it recurs as shared infrastructure across multiple frameworks, and because its GitHub repo is now archived/unmaintained, a relevant caveat for anyone relying on it via an ElizaOS plugin.
- No further genuinely distinct, comparable open-source frameworks turned up in general "open source crypto AI agent framework" / "onchain agent framework github" searches beyond the above; results otherwise reconverged on ElizaOS, GAME, and GOAT repeatedly.

## 3. Common architectural pattern

Across the frameworks confirmed real and comparable in Section 2 (ElizaOS, GAME, Rig/riglr; open-autonomy is the partial exception, noted below), a consistent shape recurs:

1. **A core LLM-driven agent loop** — perceive (via providers/context), reason (LLM call), act (via an action/tool/function call), evaluate/remember (post-hoc processing into memory) — is kept in a central runtime (ElizaOS's `AgentRuntime`; GAME's Agent orchestrating Workers/Functions; Rig's completion/tool pipeline).
2. **Blockchain capability is added as a pluggable "tool" layer, not built into the core.** ElizaOS: actions/providers via `@elizaos/plugin-*` packages. GAME: on-chain capability lives outside the core SDK, in the Virtuals platform layer and the ACP, invoked as Functions. Rig/riglr: chain interaction is a companion crate (`rig-onchain-kit`) or a separate downstream project (`riglr`) exposing Rust functions as callable tools via a `#[tool]` macro. In every case, "give this agent the ability to transfer a token" is implemented as adding a discrete, LLM-callable unit (an action / a Function / a `#[tool]`-annotated function), not as a special-cased core feature.
3. **A common interface pattern: chain operations are exposed to the LLM as callable "tools,"** structurally analogous to (and in several cases literally interoperable with) the Model Context Protocol (MCP). This is not just an analogy — it is a direct integration point in the frameworks actually researched: Rig has native MCP support in its core ([search synthesis, Rig README]), and ElizaOS has at least one community plugin (`eliza-plugin-mcp` by Fleek Platform) letting an ElizaOS agent connect outward to arbitrary MCP servers as an additional tool source, with an open core-repo issue (#844) tracking native MCP support. No equivalent MCP integration was found documented for GAME or for open-autonomy in this pass.
4. **Wallet/key management is handled as its own concern, separable from the reasoning loop**, with a spectrum of sophistication found across the frameworks: ElizaOS's chain plugins each manage their own keypair/signing (with separate opt-in plugins like `plugin-tee` and `plugin-lit` for hardened key isolation); riglr makes key isolation an explicit, named architectural pattern (`SignerContext`) specifically to keep the LLM from touching key material directly; GAME's wallet/signing lives one layer down, in the Virtuals platform rather than the open SDK. This variation is itself informative for the book chapter: the more security-conscious designs (riglr, ElizaOS's TEE/Lit plugins) treat "don't let the LLM's own token-prediction process directly control a signing key" as a first-class design problem, which is the same concern the chapter's session-key protocols (EIP-7702/ERC-4337/ERC-7715) address at the protocol layer — these frameworks are the application-layer analogue of that same problem.
5. **Multi-chain abstraction is handled by chain-scoped plugins/crates configured per agent, not a single universal chain-agnostic wallet API.** ElizaOS's `plugin-evm` covers "any viem-compatible EVM chain" generically (configuration-driven), but Solana, Aptos, and Sui each require their own distinct plugin because their transaction/account models (SVM account model vs. Move-based object/resource models) are not unifiable behind one interface — this is a real technical constraint, not a framework-design shortcoming, and it recurs identically in Rig's stack (separate Solana vs. EVM support in rig-onchain-kit/riglr).

**Open-autonomy is the outlier**, and worth calling out explicitly rather than smoothing into the above: it does not fit the "single LLM agent + tool plugins" shape at all. Its unit of composition is a quorum of redundant off-chain agent processes reaching Tendermint-based consensus before an on-chain commit, which is a fundamentally different trust model (distributed consensus among redundant agents) than "one agent, one plugin-augmented tool-calling loop, one keypair" — the pattern ElizaOS, GAME, and Rig/riglr all share. It's included in this note because it's real, open-source, and genuinely blockchain-native, but the book chapter should not describe it using the same "plugin exposes a chain action as an LLM tool" language used for the other three.
