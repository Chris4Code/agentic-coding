# Fact-check: src/rags.md (independent corroboration pass)

This is an independent web-research corroboration pass over six claims/subtopics drafted into `src/rags.md` entirely from a single Gemini "deep research" chat export (`notes/initial-notes/RAG.md`), with no prior independent verification. Corroboration tags used below, per the assignment:

- 🟢 primary — official docs/repo/paper, directly checked
- 🟡 corroborated-secondary — consistent across multiple independent write-ups
- 🟠 single-source — only one write-up found
- ⚪ could not be corroborated — no independent evidence found beyond the original chat

---

## 1. OpenAI's ChatGPT Retrieval Plugin

The chapter's "Standardized Retrieval Plugin Architecture" section states this pattern was "Originally pioneered by OpenAI's ChatGPT Retrieval Plugin" and describes three fixed endpoints: `/upsert`, `/query`, `/delete`.

**Endpoint spec — 🟢 confirmed, but incomplete.** Directly checking [github.com/openai/chatgpt-retrieval-plugin](https://github.com/openai/chatgpt-retrieval-plugin) confirms the three named endpoints exist exactly as described: `/upsert` ("allows uploading one or more documents and storing their text and metadata in the vector database"), `/query` ("allows querying the vector database using one or more natural language queries and optional metadata filters"), and `/delete` ("allows deleting one or more documents... using their IDs, a metadata filter, or a delete_all flag"). The repo also exposes a fourth endpoint the chapter doesn't mention, `/upsert-file` (single-file upload variant of `/upsert`) — a minor omission, not an error.

**Current status — 🟢 confirmed, and this is the important correction.** The repository itself is not archived (`archived: false` via the GitHub API, checked directly), still has 21,202 stars and 269 open issues, and superficially looks alive. But its actual code has not been pushed since **2024-07-04** — over two years stale as of this research (August 2026) — which lines up exactly with OpenAI's broader ChatGPT plugins wind-down. Multiple independent sources confirm: OpenAI's ChatGPT plugins system (launched alpha March 2023) stopped accepting new plugin conversations on March 19, 2024, and shut down entirely by April 9, 2024, replaced by Custom GPTs with "Actions" (GPT Store opened January 10, 2024) — see the [OpenAI developer community discussion](https://community.openai.com/t/will-chatgpt-plugins-be-discontinued-is-there-no-point-in-developing-new-plugins/543610), [GitHub issue #410 on the same repo](https://github.com/openai/chatgpt-retrieval-plugin/issues/410) ("Usage with Assistants, custom plugins has been deprecated"), and the [repo's own docs/deprecated/plugins.md](https://github.com/openai/chatgpt-retrieval-plugin/blob/main/docs/deprecated/plugins.md), which explicitly marks the old ChatGPT-plugins integration path "(deprecated)" and tells readers: "We recommend using custom actions with GPTs to make use of the Retrieval Plugin through ChatGPT." The README itself now steers people away from needing this pattern at all: "ChatGPT and the Assistants API both natively support retrieval from uploaded files, so you should use the Retrieval Plugin as a backend only if you want more granular control."

**Verdict for the chapter:** the endpoint description is accurate, but presenting the ChatGPT Retrieval Plugin as if it were a current, live, actively-relevant architecture is misleading — it is better framed as a legacy/historical reference implementation of the standardized-retrieval-endpoints pattern, not a thing anyone would deploy against live ChatGPT plugins today (that integration path is dead). The underlying *pattern* (standardize `/query`, `/upsert`, `/delete`-style endpoints so any LLM can plug into a vector store with no custom glue code) is however conceptually alive — its clearest present-day successor is Anthropic's **Model Context Protocol (MCP)**, introduced November 2024 as a standardized client-server protocol ("USB-C port for AI") for LLMs to call tools/retrievers/data sources with a common interface, addressing the same "N×M integration problem" the retrieval-plugin endpoints were solving in a narrower, single-vendor way — per [Google Cloud's MCP explainer](https://cloud.google.com/discover/what-is-model-context-protocol) and multiple comparison write-ups ([Contentful](https://www.contentful.com/blog/mcp-vs-rag/), [InfraNodus](https://infranodus.com/docs/mcp-vs-rag-vs-ai-agents)) 🟡. No source found explicitly names the ChatGPT Retrieval Plugin as a direct ancestor of MCP, so that lineage claim would be editorial framing, not a documented fact — worth phrasing as "conceptual successor," not "designed as a successor to."

## 2. `text-embedding-3-large` dimensionality and the dimension-matching constraint

**🟢 Confirmed against OpenAI's own docs.** `text-embedding-3-large` produces 3,072-dimensional vectors by default; `text-embedding-3-small` produces 1,536-dimensional vectors by default — see [OpenAI's embeddings guide](https://developers.openai.com/api/docs/guides/embeddings) and the [original "New embedding models and API updates" announcement](https://openai.com/index/new-embedding-models-and-api-updates/). The chapter's "3,072 dimensions for `text-embedding-3-large`" figure is correct.

**The nuance flagged in the task — 🟢 confirmed, and worth adding to the chapter.** Both v3 embedding models are trained with **Matryoshka Representation Learning**, and OpenAI's API exposes a `dimensions` parameter that lets a caller truncate the output vector (e.g. down to 1024 or 256 dimensions) to save storage/compute, at a modest, controlled accuracy cost, rather than the accuracy collapse a naive truncation would cause — confirmed via the [OpenAI Developer Community thread on 256 vs 3072 dimensions](https://community.openai.com/t/text-embedding-3-large-at-256-or-3072-dimensions/966400) and [Supabase's write-up on Matryoshka embeddings for OpenAI vectors](https://supabase.com/blog/matryoshka-embeddings). This complicates the chapter's "dimension matching" framing exactly as flagged: the vector DB dimensionality must match not just "the model" but the specific `dimensions` value actually requested at embedding time, since two different callers of the same model with different `dimensions` settings would produce incompatible vector spaces. The general dimension-matching principle itself (index dimensionality must match the embedding model's, or similarity search breaks) is uncontroversial and well established — this is a refinement, not a correction.

## 3. "Dual-Embedding" / "Hybrid-Embedding" architectures (local-BERT + progressively-populated cloud partition)

**⚪ Could not corroborate this as an established, named pattern.** Targeted search for "Dual-Embedding" or "Hybrid-Embedding" in the specific sense the chapter uses — routing queries between a locally-indexed BERT partition and a progressively-populated cloud-embedding partition, to defer expensive cloud embedding cost until real usage touches a chunk — turned up nothing matching that description in any paper, vendor doc, or production case study. What does exist under similar-sounding names is a different thing entirely:

- "Hybrid embedding" and "dual embedding" almost universally refer, in the actual literature, to combining **sparse (BM25/keyword) and dense (vector) retrieval** in the same query — e.g. BGE-M3's simultaneous sparse+dense+multi-vector output, or "Blended RAG" — per the [arXiv survey on optimal embedding choice in RAG](https://arxiv.org/html/2507.17442v1) and the [RAG survey paper](https://arxiv.org/pdf/2312.10997). This is a well-established, differently-defined pattern that happens to share the same name.
- Searches for the closer analogue — progressive/lazy embedding generation, embedding cost deferral, incremental promotion of content into a more expensive embedding tier — turned up only generic **embedding caching** discussions (caching identical/similar query embeddings for latency/cost savings, e.g. [Introl's embedding infrastructure guide](https://introl.com/blog/embedding-infrastructure-scale-vector-generation-production-guide-2025), [GPT Semantic Cache paper](https://arxiv.org/html/2411.05276v1)) and one academic note on "embedding recycling" ([arXiv:2207.04993](https://arxiv.org/pdf/2207.04993)) about reusing embeddings across model versions to save compute — none of which describe two parallel local/cloud embedding spaces with a query router deciding which to hit, still less a workflow where a reranker's top results get "promoted" into the cloud partition via an `/upsert`-style call.
- No Hacker News, engineering blog, or vendor architecture doc was found describing this exact scheme in production. The single HN link cited in the original Gemini chat's own footnotes (`news.ycombinator.com/item?id=35316979`) is a generic discussion thread, not a description of this architecture.

**Verdict:** this reads as a plausible-sounding architecture synthesized by the AI chat in direct response to a leading, highly specific hypothetical question ("Are there known architectures combining local embedding... and locally stored cloud embeddings... The advantage would be..."). The individual pieces are real and technically sound (local BERT embeddings, OpenAI cloud embeddings, parallel vector-DB partitions/namespaces are all real, buildable primitives — Qdrant, Milvus, and pgvector do support multiple named vector fields per collection), but the specific combination, its name ("Dual-Embedding"/"Hybrid-Embedding" in this sense), and the framing as "an active area of RAG systems engineering" could not be corroborated by any independent source. The chapter should not present this as an established/named industry pattern.

## 4. Retrieval fusion/reranking: RRF and BGE-Reranker

**RRF origin — 🟢 confirmed.** Reciprocal Rank Fusion was introduced by Gordon V. Cormack, Charles L. A. Clarke, and Stefan Büttcher in "[Reciprocal Rank Fusion outperforms Condorcet and Individual Rank Learning Methods](https://www.semanticscholar.org/paper/Reciprocal-rank-fusion-outperforms-condorcet-and-Cormack-Clarke/9e698010f9d8fa374e7f49f776af301dd200c548)," SIGIR '09 (ACM, 2009), pp. 758–759 — exactly as the source note's citation implied. The formula (score = 1/(k + rank), summed across ranked lists) is standard and confirmed by multiple technical write-ups.

**Production use — 🟢 confirmed.** Azure AI Search's hybrid search documentation directly confirms RRF is the fusion algorithm used to merge keyword and vector query results into one ranked list — see [Microsoft Learn: Relevance scoring in hybrid search using RRF](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking) and [Create a hybrid query in Azure AI Search](https://learn.microsoft.com/en-us/azure/search/hybrid-search-how-to-query) — matching the source note's citation exactly.

**BGE-Reranker — 🟢 confirmed real model family.** BAAI (Beijing Academy of Artificial Intelligence) publishes `bge-reranker-base`, `bge-reranker-large`, and newer `bge-reranker-v2-m3`/`bge-reranker-v2-gemma` cross-encoder models via its [FlagEmbedding GitHub repo](https://github.com/FlagOpen/FlagEmbedding) and [Hugging Face](https://huggingface.co/BAAI/bge-reranker-large). These are genuine, widely-used cross-encoder rerankers, consistent with the chapter's description.

No surprises here, as expected — this subtopic is well corroborated.

## 5. Cache-Augmented Generation (CAG)

**Real, named concept with a specific paper — 🟢 confirmed.** "Don't Do RAG: When Cache-Augmented Generation is All You Need for Knowledge Tasks" (Brian J. Chan et al., arXiv:2412.15605, first posted December 20, 2024; also published as [Companion Proceedings of the ACM Web Conference 2025](https://dl.acm.org/doi/10.1145/3701716.3715490)) is exactly the paper the source note was pointing at. The paper's mechanism matches the chapter's description: preload the entire relevant knowledge base into the model's extended context and cache the resulting KV state, then answer queries against that cache with no runtime retrieval step. An accompanying reference implementation exists at [github.com/hhhuang/CAG](https://github.com/hhhuang/CAG).

**The "~90%" cost-cutting figure — 🟡 corroborated, but indirectly (not from the CAG paper itself).** The CAG paper's own abstract, as directly checked, does **not** state a specific cost-reduction percentage — it claims reduced complexity, eliminated retrieval latency, and minimized retrieval errors, without quantifying token/dollar savings. The "~90%" figure instead traces to the standard cloud prompt-caching discount this book's `basics.md` chapter already documents: Anthropic prices cache reads at 0.1× the base input token price (a 90% discount), and OpenAI's newest models (GPT-5.4/5.5-era) have converged to the same ~90% cached-input discount, per general prompt-caching pricing writeups (e.g. [Anthropic prompt caching economics coverage](https://agentmarketcap.ai/blog/2026/04/06/prompt-caching-economics-2026-anthropic-google-agent-cost)). So the figure is correct as a *ceiling* tied to the underlying cache-hit discount mechanism, but attributing it to "CAG" as if the paper itself measured it is imprecise — it's really "CAG lets a static knowledge base hit that discount on effectively every query," which is a reasonable inference but not a number CAG's authors reported.

**Limitations/critiques found — 🟡 corroborated across multiple sources:**
- **Context window ceiling**: the whole knowledge base must fit in context; even 128k-token windows are infeasible for web-scale or continuously updated corpora.
- **Cache-write cost and compute**: building the KV cache for a large knowledge base is a substantial upfront cost — the KV cache grows linearly with context length and can exceed model-weight size at long contexts; one cited report found dual A100 40GB GPUs unable to scale CAG to larger knowledge bases, requiring multi-GPU tensor-parallel setups instead.
- **Staleness**: a static preload freezes the knowledge base at cache-build time; any update requires a full cache rebuild, and for frequently-changing data (stock prices, news) this recaching cycle can erase the latency/cost benefit entirely — sources explicitly recommend pairing CAG with retrieval for that case, which is exactly the chapter's own tiered-architecture motivation.

These findings (from [arXiv:2505.08261, "Enhancing CAG"](https://arxiv.org/pdf/2505.08261) and multiple secondary write-ups, e.g. [DataNorth](https://datanorth.ai/blog/cache-augmented-generation-cag-a-performance-driven-alternative-to-rag), [Analytics Vidhya](https://www.analyticsvidhya.com/blog/2025/03/cache-augmented-generation-cag/)) directly support the chapter's own framing that CAG only applies to knowledge bases "small and stable enough to fit in context" — the chapter's caveat is already correctly scoped; it just doesn't mention the cache-write cost or GPU-scaling limitation, which would strengthen it.

## 6. The chapter's "three-tier hybrid architecture" (Cold/CAG + Warm/local-BERT + Hot/cloud-embedding, with a query router)

**This is the most important finding.** Hot/warm/cold tiering is itself a genuine, established, and widely-named pattern in adjacent infrastructure — but not in the specific combination the chapter describes.

**What IS an established pattern — 🟡 corroborated:**
- **Hot/warm/cold *vector storage* tiering** (tiering by storage medium/access latency, not by embedding-model source) is a real, named, documented pattern: e.g. [Mixpeek's "Vector Storage Tiering" guide](https://mixpeek.com/guides/vector-storage-tiering) describes hot (actively-searched, in-memory), warm (on-disk, 50–200ms), and cold (object storage like S3, 200–800ms) tiers for vector databases, and a cited "three-tier hybrid architecture" example uses PostgreSQL+pgvector (hot), Pinecone/Milvus (warm), and S3-archived documents (cold) — but this tiers by *storage cost/latency*, not by *which embedding model* generated the vectors, and it has no CAG/prompt-cache component at all.
- **Hierarchical memory tiering for agents** (hot=in-context, warm=vector store, cold=archival) is also a documented pattern in agent-memory literature (e.g. [clawRxiv's Memory Tiering paper](https://clawrxiv.io/abs/2603.00037)), again without a CAG-specific "cold tier."
- **A genuine, close analogue — CAG + RAG as a two-tier hybrid** — was found and is directly relevant: multiple 2025–2026 engineering blog posts describe exactly the idea of using CAG for a stable "core" knowledge set and RAG for a dynamic "long-tail," explicitly as a hybrid/tiered router — e.g. ["RAG vs CAG: When to Stop Retrieving and Just Cache the Corpus"](https://futureagi.substack.com/p/rag-vs-cag-when-to-stop-retrieving) and ["Hybrid Architectures: Combining RAG, CAG, and Long-Context Models"](https://medium.com/@jagadeesan.ganesh/hybrid-architectures-combining-rag-cag-and-long-context-models-for-maximum-efficiency-19c6106235b0), which describe "Hybrid Tiered" systems combining CAG for "core identity/documentation" with RAG for "long-tail search," and recommend this pattern "when you have both stable core knowledge and dynamic streams." This is real and reasonably well corroborated as a *two-tier* (CAG + RAG) idea, described in industry-facing blog posts (not academic papers, and not named case studies from a specific company) 🟠/🟡 — treat as secondary-blog-level corroboration, not vendor-documented production architecture.

**What is NOT established — the chapter's specific three-way split does not appear anywhere:** No source found describes the chapter's exact construction — a Cold tier that is CAG/prompt-cache-based, a Warm tier that is specifically *locally-indexed BERT embeddings*, and a Hot tier that is specifically *cloud-native embeddings stored locally* via a retrieval-plugin-style `/upsert`, unified under one query router that first checks the CAG cache, then falls back to the (already-unverified, see subtopic 3) dual-embedding local/cloud partition scheme, then fuses/reranks and appends as a cache-safe suffix. This is a layered composition of two things this research pass found only partial support for individually (the CAG+RAG two-tier idea is a real, blogged pattern; the local-BERT/cloud-embedding dual-partition scheme in subtopic 3 is not established at all) into a three-tier whole that no case study, vendor doc, or paper was found describing.

**Verdict:** this is **not an established, named, adopted industry pattern** — it reads as a plausible, technically coherent synthesis generated by the AI chat in response to an explicit "how would you combine X (dual-embedding) with Y (CAG)?" prompt, built by layering two prior speculative answers in the same chat on top of each other. It is *technically buildable* (each individual mechanism — prompt caching, local embeddings, cloud embeddings, RRF/reranking, suffix-only prompt construction to preserve cache prefixes — is independently real and sound), but no practitioner would currently recognize "the three-tier Cold/Warm/Hot CAG+dual-embedding architecture" as a named thing, because it does not appear to exist as a described, deployed system anywhere in the literature or industry blogs surveyed. The chapter should flag this section as an illustrative/synthesized architecture pattern rather than implying it is a documented industry practice.
