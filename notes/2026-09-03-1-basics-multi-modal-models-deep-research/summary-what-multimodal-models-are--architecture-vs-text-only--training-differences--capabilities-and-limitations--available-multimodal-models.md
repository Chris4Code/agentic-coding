## Per-subtopic findings — compressed

- 🟢/🟡 **1. What multimodal models are** — an MLLM accepts >1 input modality and/or emits >1. Dominant sub-type = **vision-language model (VLM)**: image(s)+text → text; that is what "this coding model is multimodal" almost always means. Distinctions: VLM · audio-capable (bolt-on audio encoder or integrated speech stack) · **"any-to-any"/"omni"** (image/audio/video in, possibly image/audio out — GPT-4o popularized "omni", Gemini positioned native-multimodal) · image-*output* models (DALL·E / gpt-image / Gemini "Nano Banana" / FLUX — a separate lineage from VLMs). "Multimodal" is used loosely: text LLM + bolted-on encoder, vs native early-fusion pretraining, vs any product that just accepts an upload. Early–mid 2026: all frontier proprietary chat/coding models take image input as standard; **Anthropic Claude does NOT generate images** (🟢, explicit in docs); native image output is mainstream on Gemini, available via OpenAI `gpt-image`. Open reference point = **Qwen3-VL** (Apache 2.0).

- 🟢 **2. Architecture vs text-only** — three additions to a text transformer: (1) **modality encoder** — usually a **ViT**, often CLIP- or SigLIP-pretrained (Gemma 3 = 400M SigLIP @896²); splits image into patches → one vector per patch. (Fuyu-8B skips the encoder, feeds projected patches straight in.) (2) **projector/connector** — linear (original LLaVA) / 2-layer MLP (LLaVA-1.5, now default) / cross-attention resampler (Flamingo Perceiver, BLIP-2 Q-Former) / pixel-shuffle token-merge (InternVL, 4× fewer tokens; Gemma pools to fixed 256 tokens/crop). (3) **fusion**: **cross-attention** (Flamingo-style gated x-attn layers into a frozen LLM; **Llama 3.2 Vision** does this, text scores unchanged) vs **early fusion / "image patches become tokens"** (projected image tokens spliced into the same sequence, ordinary self-attention — LLaVA, Qwen-VL, Pixtral, InternVL, **Llama 4**; the dominant 2026 design). In early-fusion each image token takes a **KV-cache slot exactly like a text token** (direct tie-in to the basics.md KV-cache section). Resolution tricks: **AnyRes / dynamic tiling** (LLaVA-NeXT, InternVL, OpenAI "high" detail) · **pan-and-scan** (Gemma 3) · **native-resolution ViT** (NaViT "Patch n' Pack"; Qwen2-VL "naive dynamic resolution" + M-RoPE; Pixtral from-scratch 2D-RoPE encoder). Native-multimodal pretraining vs bolt-on: bolt-on is cheap, preserves text, trains mostly encoder+projector; native early-fusion is costlier, stronger visual reasoning, small text-regression risk. GPT-4V system card = canonical first-party "adding vision to a frontier model" writeup (no architecture disclosed). Raw file has a mermaid diagram for this.

- 🟢/🟡 **3. Training differences** — pipeline: (1) contrastive encoder pretraining (CLIP/SigLIP, 100M–B+ image-caption pairs) · (2) VL alignment stage — freeze most of LLM, train projector on noisy web image-text + **interleaved image-text** (MMC4/OBELICS style; teaches multi-image / in-context) · (3) **visual instruction tuning** — LLaVA's key trick: use a *text-only* GPT-4 to synthesize ~150K (image, instruction, response) samples from COCO captions + boxes, no human annotators; now standard · (4) preference tuning / RLHF over multimodal outputs (hallucination reduction) · (5) document/OCR/GUI-grounding data (Qwen2.5-VL / Qwen3-VL train explicitly on this). **"Vision regresses pure-text benchmarks"** — 🟡 directional only: real but small and avoidable; it's a data-mix and freezing decision, not an inherent cost. Mitigations: freeze the LLM, replay text data, or branch a vision variant from a fixed text checkpoint (Llama 3.2 Vision does the last). Data-quality issues (🟡): alt-text is SEO junk, synthetic captions propagate captioner bias, doc/GUI data is expensive → grounding/OCR ability varies a lot between models.

- 🟢/🟡 **4. Capabilities & limitations** —
  - **Do well:** OCR/text extraction (increasingly multilingual), chart/plot reading, PDF/document layout, diagram interpretation, UI screenshot understanding, captioning/VQA, some spatial reasoning, **grounding/pointing/bounding boxes** (Molmo trained on PixMo-Points for pointing+counting; Qwen2.5-VL emits boxes normalized to [0,1000]; Claude ships a coordinates guide but calls outputs "approximate").
  - **Failure modes** (🟢 — Anthropic's own vision docs enumerate most, generalize across VLMs): precise spatial reasoning / relative position, counting many small objects, reading dense or small text (esp. after downscaling; <~200px unreliable), fine high-res detail lost to downscaling, **hallucinating plausible content not in the image**, sensitivity to JPEG/WebP compression (hurts OCR), rotated/skewed images, fine geometric/CAD reasoning (🟠), can't reliably detect AI-generated images.
  - **Hazard (a): images are large, variable context-token costs** (🟢 token formulas):
    - **Claude:** 28×28-px patches, 1 token/patch, `⌈w/28⌉×⌈h/28⌉`. Standard tier ≤1568 tokens; **high-res tier (Claude 4.7+)** ≤4784 tokens, long edge ≤2576px. 1000×1000 → 1296 tokens; 1920×1080 → 2691 (high-res). **The 28×28-patch rule now supersedes the old `w×h/750` estimate** Anthropic used to publish (28×28=784≈750). ~$6.48/1000 images at 1000×1000 on Opus-tier high-res. 100 images/request (200k models) or 600 otherwise; computer-use/browser-use screenshots count toward that.
    - **OpenAI:** tile models (GPT-4o/4.1/5.x tile family) — `detail:low` = flat base (85 for 4o); `detail:high` = base + 512px-tiles × per-tile (85 + 170/tile for 4o); 1024² high ≈ 765 tok. Patch models (4.1-mini, newer 5.x) — 32×32-px patches × per-model multiplier (1.62× for 4.1-mini; ~1.2× for 5.x per the guide — 🟡 re-check).
    - **Gemini:** ≤384px both dims → flat **258 tokens**; larger → 768×768 tiles, 258 tokens each (960×540 → 6 tiles → 1548). Up to 3,600 files/request.
    - Native image *generation output* priced per-image: Gemini 2.5 Flash Image = 1290 output tokens ≈ $0.039/image.
    - **Gemma 3** (open): 256 tokens/896² crop; pan-and-scan → ~256×(N+1). Gemma-4-gen "70–1120 tokens/image" is 🟠 single community measurement (from the local-models pass).
    - **Takeaway:** an image is not "one attachment" — it's a multi-hundred-to-multi-thousand-token block competing with code for the window and KV cache; resending image history across turns multiplies it.
  - **Hazard (b): prompt injection via the visual channel** (🟡, with 🟢 vendor acknowledgement) — text embedded in a screenshot / rendered page / PDF / photo is read by OCR and treated exactly like any other prompt text; the model does not separate "look at this" from "instructions hidden in this". Indirect/cross-modal injection: faint low-contrast text, visible metadata, a screenshotted web page. Harder to sanitize than text (you can't easily preview what OCR recovers). "~64% attack success / SmoothVLM <5% defense" = 🟠 single paper. Cross-ref `src/security.md`.

- 🟢/🟡/🟠 **5. Available models (landscape 2026 — VERIFY LIVE, weakest section)** —
  - **Claude:** all current models take images (base64/URL/Files API); **native PDF** = extracted text + per-page visual render + optional page-level citations (handles scanned/layout-heavy PDFs); **no image output**; high-res vision tier since Claude 4.7. Model IDs/prices from bundled `claude-api` skill cached 2026-06-24 (🟡 verify): Fable 5 ($10/$50), Opus 5 & Opus 4.8/4.7/4.6 ($5/$25, 1M ctx), Sonnet 5 ($2/$10), Sonnet 4.6 ($3/$15), Haiku 4.5 ($1/$5, 200K) — all vision-capable, image tokens billed at normal input rate.
  - **OpenAI:** GPT-4o/4o-mini/4.1(+mini/nano)/GPT-5.x take images; `gpt-image-1` for generation; Realtime API for audio/voice. 2026 lineup (🟡/🟠 secondary — Wikipedia + pricing aggregators disagree): GPT-5 (Aug'25), 5.1 (Nov'25), 5.2 (Dec'25, 400K ctx, PDF/image in), and mid-2026 refs to GPT-5.4/5.5/5.6 ("Sol/Terra/Luna" tiers) — **treat every 5.1+ number as unverified.**
  - **Gemini:** native image+audio+video input + long context in one model; native image output in **Flash Image / "Nano Banana"** lineage (2.5 Flash Image confirmed 🟢; "Nano Banana 2" / Gemini 3.x Flash Image 🟡/🟠); **Veo** = separate video-gen line. 258-token image cost (🟢). 2026 lineup (🟡): Gemini 2.0/2.5 (Flash/Flash-Lite/Pro) + a Gemini 3.x gen — verify names/prices, don't hard-code.
  - **Open-weight VLMs** (raw file has a full table): **Qwen3-VL** (dense 2B–32B + MoE 30B-A3B/235B-A22B, Apache 2.0, 256K ctx, SOTA GUI-grounding, OCR — 🟢 arXiv:2511.21631) · **Qwen2.5-VL** (3B/7B/32B/72B, Apache 2.0, grounding, doc parsing) · **Llama 4** Scout/Maverick (native early-fusion MoE, Llama 4 Community License) · **Llama 3.2 Vision** 11B/90B (cross-attention, frozen text) · **Gemma 3/4** (SigLIP, 128K ctx, Gemma license) · **Pixtral 12B** (Apache 2.0, native-res encoder — **now deprecated by Mistral** for newer models) / Pixtral Large · **InternVL3** (MIT) · **Molmo / Molmo 2** (Ai2, Apache 2.0 + open data, pointing) · **MiniCPM-V** · **SmolVLM/SmolVLM2** (Apache 2.0, edge) · **DeepSeek-VL2** · **Phi-4 multimodal** (MIT, image+audio+text).
  - **Which back agentic coding harnesses:** proprietary frontier coders are **all multimodal already** (Claude Code, Codex/Cursor/Copilot on GPT-5.x, Gemini CLI) — vision comes "for free", you rarely pick a model *for* vision. Open-weight local agents needing vision use Qwen2.5-VL / Qwen3-VL or Gemma 3 via `libmtmd`/Ollama/LM Studio; text-only local coders (Qwen3-Coder, Devstral, GLM, gpt-oss, DeepSeek-V3.x) have **no vision path**.

- 🟡/🟠 **6. Usage in agentic coding** (product names verified Sept 2026; reliability claims practitioner-reported unless a doc is cited) —
  - **Screenshots / UI:** agent screenshots a running app / failing UI / rendered test and reasons about it — a feedback loop text-only agents lack. Claude Code accepts pasted images in the terminal (Ctrl+V; drag-drop / file-path fallbacks; platform quirks — WSL Alt+V keybinding fixed ~v2.1.157). iOS/Xcode simulator screenshot loops = practitioner-reported (🟠).
  - **Design-to-code:** **Figma Dev Mode MCP server** ("Figma MCP server") exposes a selected frame as **structured data** — component tree, variants/props, design tokens, layout, a rendered image, and (with **Code Connect**) a mapping to your real code components + imports. Works with Claude Code / Cursor / Windsurf; bidirectional Claude Code integration announced Feb 2026 (🟢). **v0** (Vercel), **builder.io** Visual Copilot = other players. Structured context (MCP + Code Connect) is **materially more reliable** than "here's a screenshot, build it"; pure screenshot-to-code drifts on spacing, colors, responsive behaviour, component reuse (🟡, not benchmarked).
  - **Visual debugging:** compare rendered output to reference, diff before/after screenshots, read DevTools screenshots, check rendered charts. VLM weaknesses bite here (small text, pixel diffs, exact colors) — pair with a real image-diff library for anything precise.
  - **Browser automation / computer use:**
    - **Anthropic** — **computer use** (`computer_toolset_20260801`, GA 2026-08-20, pixel/screenshot-based, now several actions/call) AND a **new, separate browser use** tool (`browser_toolset_20260801`) that drives an app-hosted browser via the **accessibility tree** + rendered view (semantic targeting, not pixel coords). They coexist; browser use is NOT a rename of computer use.
    - **OpenAI** — computer use tool in the Responses API, powered by **Operator / CUA** model (38.1% OSWorld, 58.1% WebVoyager at launch).
    - **Playwright MCP** (Microsoft) sends the **accessibility snapshot** not screenshots (~200–400 tokens vs thousands). Secondary benchmark: full browser task ~114K tokens over MCP vs ~27K for Playwright CLI (🟠 single benchmark).
    - **Core tension:** screenshot/pixel agents ground better on purely-visual state (canvas, custom-rendered UI) and match how humans see, but cost a big variable image-token budget every step and misread coordinates; a11y-tree/DOM agents are **20–50× cheaper** and click exactly, but are blind to non-DOM rendering and break on inaccessible widgets. Consensus: **a11y tree primary, screenshot fallback.** Stale-snapshot accumulation is a known failure mode.
  - **Diagrams:** reading architecture/ER/sequence diagrams and whiteboard photos; generating Mermaid from a sketch and validating the render. Decent on clean diagrams, weak on messy handwriting (🟠).
  - **PDF / documents:** feed spec PDFs / API docs / RFCs / scans. Claude native PDF = text + per-page render + page citations. **Alternative: PDF-to-markdown preprocessors** — **docling** (IBM), **marker**, **MinerU**, `pymupdf4llm` — far fewer tokens, deterministic, greppable, cacheable as text; but conversion errors on complex layouts, loss of figures. Rule of thumb: native vision-PDF for a few pages / layout-heavy; converter for large or repeatedly-queried docs where token budget dominates.

- **7. Relevance — multimodal vs text-only coder** (analysis; supporting facts 🟢 from §4–5) — **Costs of vision:** big variable context-token block per image competing with code for window + KV cache; locally also VRAM + quant-sensitive encoder + smaller usable context (see local-models pass); small text-regression risk if training mix unmanaged. **Text-only coder wins for:** pure codegen, refactoring, tests, review, terminal/repo work — cheaper per turn. **Multimodal is the point for:** frontend/UI implementation against a mockup, closing the visual feedback loop, consuming visual specs (Figma, diagrams, spec PDFs, whiteboard photos), browser/computer-use agents. **Key framing: the choice mostly only arises for local / open-weight setups** — every frontier proprietary coding model is already a VLM, so a cloud user gets both; the real decision is local (text-only coder and give up screenshots, vs VLM backbone + overhead, vs text coder + separate small perception VLM).
