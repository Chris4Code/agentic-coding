## 1. Public DLTs (umbrella/intro)

A distributed ledger is a data store replicated, shared, and synchronized across a network of independently operated nodes, with no central administrator holding a canonical write copy 🟢 [Cornell LII: distributed ledger technology (DLT)](https://www.law.cornell.edu/wex/distributed_ledger_technology_(dlt)). Three properties matter for software-engineering purposes:

- **Write access model**: A DLT network can be *permissionless* (anyone can run a node and submit/validate transactions, no vetting) or *permissioned* (only pre-approved participants may write) 🟢 [Cornell LII](https://www.law.cornell.edu/wex/distributed_ledger_technology_(dlt)). "Public" in this chapter always refers to permissionless networks (Ethereum, Solana, Sui, Aptos, IOTA, etc.), as distinct from private (single-org) or consortium/permissioned chains run by a fixed set of vetted institutions 🟢 [TechTarget: permissioned vs. permissionless blockchains](https://www.techtarget.com/searchcio/tip/Permissioned-vs-permissionless-blockchains-Key-differences).
- **Consensus and finality**: nodes agree on ledger state via a consensus algorithm (proof-of-stake variants dominate current major public networks) rather than a trusted operator; "finality" is the point past which a transaction is (practically or provably) irreversible. Finality times vary enormously by network — this is covered concretely in subtopic 8.
- **Smart-contract execution environment**: most networks relevant here are *programmable* — they run a general-purpose virtual machine (EVM, MoveVM, SVM) that executes user-deployed code deterministically across all nodes, not just a value-transfer ledger.

🟡 corroborated-secondary: The general engineering trade-off — decentralization/tamper-resistance and cross-org neutrality bought at the cost of throughput, latency, and operational complexity versus a centralized system — is consistently described across vendor-neutral and critical sources alike (see subtopic 3).

## 2. What it is

"Blockchain" and "DLT" are not synonyms: a blockchain is one specific data structure (an append-only, cryptographically hash-linked chain of batched transactions) used to implement a distributed ledger; DLT is the broader category encompassing any replicated, synchronized ledger design, including non-chain topologies 🟢 [Cornell LII](https://www.law.cornell.edu/wex/distributed_ledger_technology_(dlt)); 🟡 [Ram Vadranam: DLT — permissioned vs. permissionless, blockchain, DAG, consensus](https://ramchandra-vadranam.medium.com/distributed-ledger-technology-dlt-a-comprehensive-guide-to-permissioned-vs-5b380683180a).

Three families are relevant to this chapter's later sections:

- **Account-based EVM chains** (Ethereum, Base, Gnosis Chain): state is a set of accounts (externally-owned or contract) with balances/storage, and every transaction execution model derives from Ethereum's original account model.
- **Object-centric Move-based chains** (Sui — and, since May 2025, IOTA at L1): assets are first-class *objects* with explicit ownership, so transactions that touch disjoint objects have no data dependency and can be validated/executed in parallel without global sequencing 🟢 [Sui docs: Programmable Transaction Blocks](https://docs.sui.io/concepts/transactions/prog-txn-blocks); 🟡 [AeorysAnalytics: Sui vs Aptos Move deep dive](https://aeorysanalytics.medium.com/sui-vs-aptos-a-technical-deep-dive-into-move-language-implementations-b2c2c8132dd6).
- **Account-based Move chains** (Aptos): also uses the Move language but, unlike Sui, keeps an account-centric global-storage model close to Move's Diem/Libra ancestry, relying on Block-STM optimistic parallel execution (detect-and-re-execute conflicting transactions) rather than Sui's object-ownership parallelism 🟡 [BlockEden: Aptos vs Sui in 2026](https://blockeden.xyz/blog/2026/03/11/aptos-vs-sui-move-language-twin-stars-compared/); 🟡 [cryptonews.net: Aptos vs Sui, same language different architecture](https://cryptonews.net/news/altcoins/33351345/). Seed chat 1's claim that Aptos "uses the standard, transaction-centric Diem variant of the Move language" is directionally correct (Aptos Move does descend from Diem) but its further claim that ElizaOS agents on Aptos "execute PTBs (Programmable Transaction Blocks)" is ❌ inaccurate — PTB is Sui/IOTA terminology (see subtopic 7); Aptos does not use that term or mechanism for its transaction model.
- **DAG-based ledgers**: IOTA's original (pre-2025) architecture used a Directed Acyclic Graph ("Tangle") rather than a blockchain. This changed materially with the May 2025 "Rebased" upgrade (see subtopics 7–8) — the current IOTA L1 is no longer a pure DAG-Tangle design for smart-contract execution.

## 3. When to use in general

Well-corroborated, vendor-neutral guidance converges on the same shape of answer: a public DLT is justified when you need (a) tamper-evident state that multiple **mutually distrusting** parties must agree on without a shared trusted intermediary, (b) censorship-resistance/neutrality (no single operator can unilaterally change or revoke access), and (c) programmable, publicly verifiable execution. A conventional centralized/Web2 system remains the better engineering choice whenever a trusted operator already exists, when throughput/latency/cost matter more than decentralization, or when the data is sensitive and doesn't need public verifiability 🟢 [TechTarget: blockchain vs. traditional database](https://www.techtarget.com/searchcio/tip/Blockchain-vs-database-Similarities-differences-explained); 🟢 [Chainlink: blockchain vs. database](https://chain.link/article/blockchain-vs-database); 🟡 [CompTIA decision-tree PDF: when is blockchain or another database the right choice](https://comptiacdn.azureedge.net/webcontent/docs/default-source/research-reports/blockchain-decision-tree.pdf?sfvrsn=d2e83a7_0).

**Research Note:** the critical/counter-argument literature is substantial and should not be omitted. Multiple independent sources — industry press, an operations-management peer-reviewed study, and practitioner retrospectives — converge on "blockchain is a solution in search of a problem" as a fair characterization of the majority of enterprise blockchain pilots from the 2017–2022 wave: most failed not for technical reasons but because blockchain was proposed to solve a *coordination* problem among organizations that had not first solved the prior, more basic problem of agreeing to adopt a shared system at all 🟡 [CIO.com: RIP (finally) to the blockchain hype](https://www.cio.com/article/3838169/rip-finally-to-the-blockchain-hype.html); 🟡 [Wiley/Journal of Operations Management: success and failure of blockchain technology providers](https://onlinelibrary.wiley.com/doi/10.1002/joom.1364); 🟡 [Forbes: why enterprise blockchain projects fail](https://www.forbes.com/sites/dantedisparte/2019/05/20/why-enterprise-blockchain-projects-fail/); 🟡 [Frontiers in Blockchain: TradeLens failure case study](https://www.frontiersin.org/journals/blockchain/articles/10.3389/fbloc.2025.1503595/full). A recurring, credible technical critique is that for a *permissioned/consortium* setting with an already-agreed-upon governance structure, a DLT frequently "doesn't differ substantially from traditional database software" run with standard access control and audit logging — the specific value-add of decentralization (no single administrator, permissionless entry) is what's actually being paid for in throughput and complexity, and that value-add is often absent or unwanted in an enterprise consortium context. This chapter's later sections (4–5) argue that the calculus changes specifically once the participants are mutually distrusting autonomous *agents* rather than consortium members with legal agreements — a distinction worth stating explicitly rather than assuming.

## 4. Public DLTs for Agentic Fabrics (why, in general)

The core, well-corroborated argument specific to AI agents (not narrowly software factories) is that traditional financial/identity rails assume a human principal: bank accounts, card processors, and OAuth logins are built around KYC'd human or corporate identity, business hours, and manual approval flows, none of which fit an autonomous, always-on software process that needs to hold and spend value or prove who it is without a human in the loop 🟡 [Fireblocks: agentic finance & stablecoins report](https://www.fireblocks.com/report/agentic-finance-stack-ai-commerce). Public/permissionless rails let a cryptographic keypair *be* the payable, authenticatable identity, independent of a bank's or platform's willingness to onboard a non-human actor.

**Verifying the named projects from the seed chats:**

- **Skyfire** — real, active. It is a payment network specifically built for AI-agent-to-agent transactions, offering programmatic wallets, verifiable agent identity ("KYA" — know-your-agent), and funding via cards/ACH/wire/USDC on Base; it exited beta in March 2025 🟢 [Skyfire product page](https://skyfire.xyz/product/); 🟢 [Businesswire: Skyfire exits beta](https://www.businesswire.com/news/home/20250306938250/en/Skyfire-Exits-Beta-with-Enterprise-Ready-Payment-Network-for-AI-Agents). The seed chat's characterization is accurate.
- **Coinbase Developer Platform (CDP) + MPC wallets** — real, active, and more developed than the seed chat implies. As of February 2026, Coinbase ships "Agentic Wallets": MPC-secured, non-custodial-key wallets with programmable session caps, per-transaction spend limits, gasless settlement on Base, native x402 support, and an MCP-server interface usable directly from Claude, Codex, or Gemini; the underlying developer toolkit is open-source (`coinbase/agentkit`) 🟢 [Coinbase: empowering AI agents with programmable MPC wallets](https://www.coinbase.com/developer-platform/discover/launches/empower-ai-agents); 🟢 [Coinbase docs: Agentic Wallet](https://docs.cdp.coinbase.com/agentic-wallet/welcome); 🟢 [GitHub: coinbase/agentkit](https://github.com/coinbase/agentkit).

## 5. Why, specifically for Software Fabrics

Narrowing to *software development* factories specifically, two claims from the seed chats need separate scrutiny: (a) tokenizing build artifacts via ERC-721/ERC-1155, and (b) the LangChain-off-chain/DLT-on-chain hybrid orchestration pattern.

**Tokenizing build artifacts (ERC-721/ERC-1155) — ❌ largely speculative framing, not an established practice.** ERC-721 and ERC-1155 are real, standard, and heavily used token standards — ERC-721 for strictly unique non-fungible tokens with built-in ownership/provenance tracking, ERC-1155 as a more gas-efficient multi-token standard covering both fungible and non-fungible assets in one contract 🟢 [Chainlink: ERC-721 vs ERC-1155](https://chain.link/article/erc-721-vs-erc-1155); 🟢 [Wikipedia: ERC-721](https://en.wikipedia.org/wiki/ERC-721). However, no evidence was found — across general search and targeted queries — of ERC-721/1155 being used or credibly, concretely proposed specifically to mint compiled builds or pull requests as tokens referencing an immutable creation-history hash, the way the seed chat describes. This should be presented as a *plausible extrapolation* of well-established NFT provenance mechanics onto a new (software-artifact) domain, not as a documented or observed practice. ERC-8004's Identity Registry (subtopic 9) is the closest real, concretely specified use of ERC-721 adjacent to "agent" provenance, and even that tokenizes agent identities, not build artifacts.

**On-chain vs. off-chain orchestration ("LangChain as brain, DLT as backbone") — 🟠 single-source / not independently documented as a named pattern.** No primary or independent secondary source was found describing this specific "hybrid model" terminology or architecture as a documented, credible industry pattern; it appears to originate from the seed chat's own reasoning rather than from an external source. That said, the *underlying engineering logic* is sound and consistent with general distributed-systems practice: keeping expensive, non-deterministic, and stateful work (LLM inference, prompt chaining, log parsing) off a metered, deterministic execution environment, while using the ledger only for the specific sub-problem it is uniquely good at — atomic, trust-minimized settlement/state-commitment across mutually distrusting parties — matches how production Web3 systems generally treat blockchains (as a settlement/coordination layer, not a general compute layer). Frame this in the chapter as *reasoned architectural inference*, explicitly flagged as not independently corroborated as a named pattern, rather than as an established practice with its own citation trail.

**Code provenance / paying agents for discrete SDLC contributions** is the strongest, most concretely evidenced part of this subtopic, but the evidence lives in the *protocols* (subtopic 9) rather than in named "software factory" case studies: ERC-8004's on-chain Identity/Reputation/Validation registries are explicitly designed to be payment-mechanism-agnostic and interoperable with MCP and the Agent2Agent (A2A) protocol 🟢 [ERC-8004 spec](https://eips.ethereum.org/EIPS/eip-8004), and x402/MPP (subtopic 9) are explicitly built for exactly the "agent pays API/agent per discrete unit of work" pattern the seed chats describe (linting, compiling, testing). No named, real "decentralized software factory" product or case study using this full stack together was found — this remains a coherent but currently hypothetical composition of independently real building blocks.

## 6–7. Which DLT network to use / Requirements

The choice of network is driven by four largely independent axes, each covered with primary or strong secondary sourcing:

1. **Transaction throughput/finality speed** — needed for agent-paced (sub-second to few-second) interaction loops, not human-paced approval flows.
2. **Cost per transaction** — critical specifically for micropayments/nanopayments (sub-cent contributions), where fees above the payment amount make the model uneconomical.
3. **Atomic multi-step transaction support** — needed to bind "work verified" and "payment released" into a single all-or-nothing state transition (this is where the seed chats' PTB claims live; verified below).
4. **Identity/authorization primitives** — account abstraction and session-scoped keys, so an agent can hold *bounded* signing authority rather than a master key (EIP-7702/ERC-4337/ERC-7715, covered in subtopic 9).

**Programmable Transaction Blocks (PTBs) — 🟢 real, and Sui-originated (also now on IOTA); NOT a general Move-ecosystem or Aptos feature.** PTBs are a genuine, primary-documented Sui mechanism: a PTB is a heterogeneous, composable sequence of up to 1,024 Move-function-call "commands" that execute in order within one transaction, with results able to flow between commands, and the entire block's effects (object mutations, transfers) applied atomically at the end — if any command fails, the whole block is rolled back 🟢 [Sui docs: Programmable Transaction Blocks](https://docs.sui.io/concepts/transactions/prog-txn-blocks). IOTA's post-Rebased (see below) L1 documents the identical PTB mechanism, since IOTA's new Move-based execution layer shares lineage with Sui's Move implementation 🟢 [IOTA docs: use Programmable Transaction Blocks](https://docs.iota.org/developer/iota-101/transactions/ptb/programmable-transaction-blocks). Sui transaction finality is commonly reported around ~400ms 🟡 [cryptonomist: Sui atomic transactions AI execution](https://en.cryptonomist.ch/2026/08/21/sui-atomic-transactions-ai-execution/). **Correction to seed chat 1**: PTBs are not an Aptos feature (Aptos uses a different, account-based execution and parallelism model — Block-STM — with no "PTB" terminology); the seed chat's claim that ElizaOS agents "execute PTBs" on Aptos is inaccurate.

**"IOTA Rebased" — 🟢 accurate, current terminology as of the sources found (2026).** IOTA underwent its largest-ever mainnet upgrade on May 5, 2025 (approved by token-holder vote in December 2024), rebranded/rearchitected as "IOTA Rebased": full decentralization, native staking, Move-VM-based Layer-1 smart contracts (making IOTA the third network after Aptos and Sui to run MoveVM at L1), and throughput benchmarked above 50,000 TPS 🟢 [IOTA Foundation blog: the IOTA Rebased mainnet upgrade](https://blog.iota.org/rebased-mainnet-upgrade/); 🟡 [crypto.news: IOTA Rebased protocol upgrade](https://crypto.news/iota-to-undergo-major-mainnet-upgrade-to-rebased-protocol-in-may/). "IOTA Rebased" remains the name used in IOTA's own current documentation and blog as of the most recent sources found — it has not been superseded by a different official name (no evidence of a rename to e.g. "IOTA Move"). Note this is a substantive architecture change from IOTA's historical identity as a pure DAG/"Tangle" ledger — current IOTA smart-contract execution is Move-VM-based, not DAG-based; the DAG/Tangle framing from IOTA's earlier years no longer describes the current L1 smart-contract environment accurately.

## 8. Suitable existing Networks

- **Ethereum** — mainnet: highest security/decentralization guarantees and richest agent-tooling ecosystem, but the highest cost/slowest finality among peers (~13 min finality; $0.50–$5+ typical L1 fees in the sources found) 🟡 [Cobo: Solana vs Ethereum 2026](https://www.cobo.com/post/solana-vs-ethereum-comparison). Carries EIP-7702 (shipped, Final) and the ERC-4337 ecosystem natively (subtopic 9).
- **Base** (Coinbase's Ethereum L2) — ~2s blocks, ~7 min L1-anchored finality, fees generally $0.01–$0.30 🟡 [Cobo](https://www.cobo.com/post/solana-vs-ethereum-comparison). This is where Coinbase's own Agentic Wallets and x402 default to settling (subtopic 4), giving it the most mature agent-payment tooling of any EVM chain found in this research.
- **Solana** — fastest/cheapest EVM-alternative among sources found: ~400ms block time, ~2.5s finality, fees as low as $0.0001–$0.01 (some sources cite ~$0.00025 average) 🟡 [Cobo](https://www.cobo.com/post/solana-vs-ethereum-comparison); 🟡 [BingX: SOL vs ETH transaction costs 2026](https://bingx.com/en/answers/smart-choices-battle-of-the-assets/sol-vs-eth-comparing-2026-transaction-costs). Uses the SVM, not EVM or MoveVM — a genuinely distinct smart-contract runtime, relevant when assessing tooling portability.
- **Gnosis Chain** — 🟡 no direct cost/finality figures were found in this pass (search did not surface Gnosis-specific 2026 numbers), but its de facto relevance here is empirical: it is the dominant settlement chain for the Olas/Autonolas agent-swarm ecosystem, carrying the large majority of Olas's 18M+ cumulative agent transactions (subtopic 4) 🟡 [agenteconomy.to](https://agenteconomy.to/olas) — i.e., its suitability is evidenced by existing agent-economy usage rather than by a specific throughput/cost claim.
- **Sui** — Move-VM, object-centric parallel execution, PTBs for atomic multi-step agent workflows (subtopic 7), ~400ms finality 🟡 [cryptonomist](https://en.cryptonomist.ch/2026/08/21/sui-atomic-transactions-ai-execution/). Strongest technical fit among sources found for the "atomic multi-agent settlement" use case specifically.
- **Aptos** — Move-VM, account-based, Block-STM optimistic parallelism; closer to Ethereum's mental model for developers migrating from EVM, per secondary sourcing 🟡 [BlockEden: Aptos vs Sui 2026](https://blockeden.xyz/blog/2026/03/11/aptos-vs-sui-language-twin-stars-compared/).
- **IOTA (post-Rebased)** — now MoveVM-based at L1 with PTB support and >50,000 TPS benchmarked throughput 🟢 [IOTA Foundation blog](https://blog.iota.org/rebased-mainnet-upgrade/); also runs a parallel **IOTA EVM** side chain (Chain ID 8822, confirmed 🟢 [chainid.network: IOTA EVM](https://chainid.network/chain/8822/); sub-cent gas, ~2s blocks, >1,000 TPS benchmark, standard Ethereum JSON-RPC 🟡 [Uniblock docs: IOTA EVM overview](https://docs.uniblock.dev/reference/jsonrpc-docs/8822/iota-evm-overview)) for EVM-native tooling compatibility — confirming seed chat 1's Chain ID claim and its "dual-path" (EVM + Move) characterization of IOTA's architecture.

**Research Note:** none of these figures should be read as stable — public-network throughput/cost/finality numbers shift with protocol upgrades and network load, and the 2026-dated figures found here reflect a fast-moving competitive landscape rather than settled facts.

## 9. Relevant protocols and standards

### x402 — 🟢 primary-sourced. Real, shipped, actively governed.
Originally contributed by Coinbase, x402 revives the HTTP `402 Payment Required` status code for machine-native, per-request payments: a server responds `402` with price/payment details, the client (agent) attaches a signed on-chain stablecoin payment payload, and retries the request 🟢 [x402 Foundation launch announcement](https://x402.org/linux-foundation-announces-operational-launch-of-x402-foundation-to-standardize-internet-native-payments-for-ai-agents-and-applications/). **The Linux Foundation governance claim is confirmed accurate**: Coinbase and Cloudflare announced intent in September 2025, the Linux Foundation formalized the x402 Foundation in April 2026, and announced full operational launch on July 14, 2026, with 40 member organizations (including Coinbase, Circle, Visa, Mastercard, AWS, American Express, Google, and Stripe) under open, vendor-neutral governance — Coinbase contributed the protocol but does not control its evolution 🟢 [Linux Foundation press release](https://www.linuxfoundation.org/press/linux-foundation-announces-operational-launch-of-x402-foundation-to-standardize-internet-native-payments-for-ai-agents-and-applications). **Status for a software factory: mandatory/foundational** for any per-request agent-to-service payment use case. **Availability**: chain-agnostic by design; commonly implemented with USDC on Base and Solana in the sources found.

### EIP-7702 — 🟢 primary-sourced. Shipped, Final, Ethereum/EVM-only.
Confirmed via the EIP itself: title "Set Code for EOAs," status **Final**, shipped in the Pectra hard fork at Ethereum mainnet slot 11649024 on **May 7, 2025** 🟢 [EIP-7702 spec](https://eips.ethereum.org/EIPS/eip-7702); 🟢 [Quicknode: Pectra upgrade](https://www.quicknode.com/guides/ethereum-development/ethereum-upgrades/pectra-upgrade). It defines a new transaction type letting an EOA attach an authorization tuple that makes the account's code point at (delegate to) a smart contract, enabling batched calls, gas sponsorship, and privilege de-escalation to sub-keys. **One correction to both seed chats' framing**: the EIP itself specifies this as a persistent delegation (the EOA's code is set until explicitly changed again), not an inherently time-limited "session" — the "session key," self-expiring, scoped-permission framing used by both seed chats is an *application-layer pattern built on top of* EIP-7702 (typically combined with ERC-7715, below), not something EIP-7702 itself enforces as a protocol-level time limit. **Status: mandatory/foundational for any Ethereum/EVM agent-factory design** wanting scoped agent signing authority without deploying a separate smart-contract wallet. **Availability**: Ethereum/EVM-only (this is an Ethereum protocol-level transaction type, not portable to Sui/Aptos/Solana).

### ERC-4337 — 🟢 primary-sourced (well-established, pre-dates EIP-7702).
Account Abstraction: standardizes a smart-contract "EntryPoint" plus off-chain bundlers and on-chain "paymasters" to relay/sponsor "UserOperations," requiring a separately deployed smart-contract wallet and no hard fork. It is **complementary to, not competing with, EIP-7702** — most production wallet stacks (Safe, Biconomy, ZeroDev, Alchemy) support both, and a 7702-delegated EOA can itself sign UserOperations that flow through the standard 4337 EntryPoint 🟡 [BuildBear: ERC-4337 vs EIP-7702](https://www.buildbear.io/blog/eip-4337-7702-comparison); 🟡 [Turnkey: account abstraction from ERC-4337 to EIP-7702](https://www.turnkey.com/blog/account-abstraction-erc-4337-eip-7702). **Status: mandatory/foundational** for enforcing custom validation logic (daily caps, human co-signing) at the wallet layer. **Availability**: Ethereum/EVM-only.

### ERC-7715 — 🟢 primary-sourced. Real draft ERC, directly implements "session keys."
"Grant Permissions from Wallets" (draft ERC, authored by Derek Chiang, Lukas Rosario, Wilson Cusack, Dror Tirosh, Jake Moxey), adding a `wallet_grantPermissions` JSON-RPC method 🟢 [ERC-7715 spec](https://eips.ethereum.org/EIPS/eip-7715); 🟢 [MetaMask docs: ERC-7715 request permissions](https://docs.metamask.io/delegation-toolkit/0.12.0/experimental/erc-7715-request-permissions/). It introduces the "session account" concept — a temporary, fund-holding-free identity a dApp/agent creates to request/redeem scoped permissions (by token, amount, contract, function selector, time window), enforced at the smart-account's permission-validator module. This is the standard that actually delivers the scoped, self-expiring "session key" behavior both seed chats attribute more loosely to EIP-7702 — ERC-7715 and EIP-7702 are complementary, commonly composed together (matches seed chat 1's architecture diagram). **Status: optional but high-value** — the concrete permission-scoping layer that makes EIP-7702/ERC-4337 usable for a bounded-trust autonomous agent. **Availability**: Ethereum/EVM-only.

### ERC-8004 "Trustless Agents" — 🟢 primary-sourced. Real ERC number; confirmed **Draft** status (not finalized).
Confirmed via the EIP repository itself: **ERC-8004**, "Trustless Agents," status **Draft** 🟢 [ERC-8004 spec](https://eips.ethereum.org/EIPS/eip-8004). It defines three on-chain registries — Identity (ERC-721-based portable agent identifiers resolving to off-chain capability/endpoint descriptions), Reputation (feedback-signal recording/querying), and Validation (requesting/recording independent work verification via re-execution staking, ZK proofs, or TEEs) — explicitly designed to be payment-mechanism-agnostic and interoperable with MCP and the Agent2Agent (A2A) protocol 🟢 [ERC-8004 spec](https://eips.ethereum.org/EIPS/eip-8004). It was proposed August 13, 2025, authored by contributors from MetaMask, the Ethereum Foundation, Google, and Coinbase, and by Q2 2026 had reference implementations live on Base Sepolia, Linea Sepolia, and Hedera Testnet as well as mainnet 🟡 [QuickNode: ERC-8004 developer's guide](https://blog.quicknode.com/erc-8004-a-developers-guide-to-trustless-ai-agent-identity/). An arXiv empirical study of the live ERC-8004 ecosystem was also found, indicating real (not purely theoretical) deployment activity 🟡 [arXiv: empirical study of the ERC-8004 ecosystem](https://arxiv.org/pdf/2606.26028). **Status: important/emerging but not yet a finalized standard** — treat as a credible, actively-developed draft with real reference deployments, not a settled foundation to build on unconditionally. **Availability**: Ethereum/EVM (with cross-chain testnet reference deployments); no direct Sui/Aptos/Solana equivalent identified in this research.

### "MPP" / Machine Payment(s) Protocol — 🟢 primary-sourced; **the seed-chat contradiction is resolved decisively in favor of seed chat 2, with a correction.**
Fetched directly from the protocol's own specification repository: MPP is co-authored by **Tempo and Stripe**, explicitly **not** built on Bitcoin's Lightning Network, and instead "network agnostic and multi-rail," supporting bank rails, cards, and stablecoins through a layered architecture (core HTTP mechanics → abstract payment intents → concrete per-network implementations → optional discovery/identity extensions) 🟢 [GitHub: tempoxyz/mpp-specs](https://github.com/tempoxyz/mpp-specs); 🟢 [Stripe: introducing the Machine Payments Protocol](https://stripe.com/blog/machine-payments-protocol). It launched March 18, 2026 alongside the Tempo mainnet (a payments-focused blockchain co-developed with Paradigm), reusing the same `402` status code as x402 but targeting session-based spending allowances rather than x402's strict per-request model, with reported support/interest from Visa, OpenAI, Mastercard, and Shopify 🟡 [thedefiant.io: Tempo mainnet launch and MPP](https://thedefiant.io/news/blockchains/tempo-launches-mainnet-unveils-machine-payments-protocol-with-stripe). **Resolution**: seed chat 1's description ("Bitcoin Lightning Network," per-millisecond streaming) is ❌ inaccurate and should be corrected in the chapter. Seed chat 2's description (Stripe/Tempo-backed, session-based allowance model, contrasted with x402's per-request model) is 🟢 accurate and should be the one used. One nuance to add beyond seed chat 2: MPP is explicitly multi-rail (not exclusively crypto), so it is not a pure-DLT protocol in the way x402 typically is in practice — it's a payment-authorization protocol that *can* settle over Tempo's chain or other rails. **Status: optional/emerging** — very new (launched 2026), real, but adoption-stage evidence is thinner than x402's. **Availability**: Tempo chain (native) plus, per the spec's multi-rail design, other payment rails via its "concrete implementation" layer — not confirmed as available on Sui/Aptos/Solana specifically.

### AP2 "Agent Payments Protocol" — 🟢 primary-sourced. Real, Google-originated, actively transferring governance.
Announced by Google on September 16, 2025 with 60+ payments/technology partners (PayPal, Mastercard, Amex, Adyen, Coinbase, Salesforce, ServiceNow, Etsy, and more), AP2 is an open, payment-method-agnostic protocol giving an agent a verifiable, cryptographically signed "permission slip" from a human before spending on that human's behalf, supporting cards, bank transfers, and cryptocurrencies 🟢 [Google Cloud blog: announcing AP2](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol). As of the most recent source found, Google is **donating AP2 to the FIDO Alliance** to make it platform-agnostic/community-led going forward 🟢 [Google: donating AP2 to FIDO Alliance](https://blog.google/products-and-platforms/platforms/google-pay/agent-payments-protocol-fido-alliance/) — this is a governance detail not present in either seed chat and worth including. **Status: optional but strategically significant** — most relevant for the agent-to-agent authorization/intent-delegation use case (e.g., a manager agent authorizing a sub-agent's spend), complementary to rather than competing with x402/MPP's request-settlement mechanics. **Availability**: payment-method-agnostic by design (cards, bank rails, and crypto), not tied to a specific chain.

### W3C DID and Verifiable Credentials — 🟢 primary-sourced. Real, mature W3C standards; current spec activity confirmed.
Both are genuine W3C specifications with an active, ongoing standardization process. DIDs: a Candidate Recommendation Snapshot of **DID v1.1** was published March 5, 2026 (updating the 2022 v1.0 Recommendation), open for public comment 🟢 [W3C: DID v1.1](https://www.w3.org/TR/did-1.1/); 🟡 [Biometric Update: W3C releases updated DID spec](https://www.biometricupdate.com/202603/w3c-releases-updated-decentralized-identifiers-spec-for-comment). Verifiable Credentials: as of the sources found, nearly all VC-family documents have reached full W3C Recommendation status, with a new revision cycle underway in 2026 🟡 [W3C: Verifiable Credentials Overview](https://www.w3.org/TR/vc-overview/). Application specifically to *AI agent* identity (as opposed to human/organizational identity, the standards' original target) is early-stage: one named example was found (Nuggets building an AI-agent authentication product on DIDs) 🟠 single-source for that specific application, though the underlying DID/VC standards themselves are 🟢 primary-sourced and mature. **Status: optional/emerging for agent use specifically** — mature standards being *repurposed*, not standards purpose-built for agent identity (contrast with ERC-8004, which was purpose-built for this). **Availability**: chain-agnostic — DIDs/VCs are a data-model/spec layer that can anchor to any DLT or off-chain registry.

### Model Context Protocol (MCP) — 🟢 primary-sourced; kept brief per scope (likely covered elsewhere in the book).
Confirmed: created by Anthropic, released as an open standard in November 2024, and by 2026 reached industry-standard adoption levels — ~97 million monthly SDK downloads, native support across Claude, ChatGPT, Gemini, Copilot, VS Code, and Cursor, and was donated to the Linux Foundation's newly formed **Agentic AI Foundation** (co-founded with Block and OpenAI) on December 9, 2025 🟢 [Wikipedia: Model Context Protocol](https://en.wikipedia.org/wiki/Model_Context_Protocol); 🟡 [digitalapplied.com: MCP adoption statistics 2026](https://www.digitalapplied.com/blog/mcp-adoption-statistics-2026-model-context-protocol). Relevance to DLT-anchored audit logging specifically: MCP standardizes the tool-connection layer through which an agent's actions (repo access, compiler/test invocations) pass — making it a natural point to *log* actions before any hash or checkpoint of that log is anchored to a DLT, but MCP itself has no built-in DLT-anchoring behavior; that would be a separate integration layered on top. ERC-8004 explicitly lists MCP as one of the protocols it's designed to interoperate with (subtopic above), which is the most concrete tie between MCP and the DLT-agent-identity stack found in this research.

### ERC-721 / ERC-1155 for build artifacts — 🟡 standards are real; the specific application is speculative.
See subtopic 5 above for the full assessment — the token standards themselves are real and well-established 🟢 [Chainlink: ERC-721 vs ERC-1155](https://chain.link/article/erc-721-vs-erc-1155), but no evidence was found of this specific application (tokenizing compiled builds/PRs) being practiced or concretely proposed outside the seed chat's own framing. **Status: speculative/optional** — present as a plausible extrapolation, explicitly flagged as unverified, not as an existing practice.

### Reclaim Protocol and TLSNotary — 🟢 primary-sourced; the "prove tests passed without revealing logs" characterization is accurate.
Both are real, active zkTLS ("Web Proofs") projects that let a party generate a cryptographic proof that specific data was received from a specific TLS-secured web source, without revealing the underlying data itself. TLSNotary pioneered the MPC-based (multi-party computation) approach; Reclaim Protocol uses a proxy-witness model with fast (2–4 second) mobile-generated proofs across hundreds of data sources, layering zero-knowledge proofs on top of TLS session verification 🟢 [Reclaim Protocol blog: the zk in zkTLS](https://blog.reclaimprotocol.org/posts/zk-in-zktls); 🟢 [GitHub: Reclaim Protocol](https://github.com/reclaimprotocol); 🟡 [Shoal Research: zkTLS verifiable data composability](https://www.shoal.gg/p/zktls-verifiable-data-composability). Documented real-world use cases include income verification for undercollateralized lending, Sybil-resistant airdrop qualification via off-chain activity, and proof-of-personhood — all structurally identical in shape to "prove a test suite passed without uploading the logs," which is a fair, accurate characterization of what this technology class does, even though a CI-test-suite-specific example was not directly documented in the sources found. **Status: optional, but the most technically apt tool found for the specific audit-without-disclosure use case** the seed chat describes. **Availability**: TLS/web-based, chain-agnostic in principle for the proof-generation step; on-chain verification integrations exist across multiple ecosystems including Solana 🟡 [Solana Compass: Reclaim Protocol on Solana](https://solanacompass.com/projects/reclaim-protocol).
