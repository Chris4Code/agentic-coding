## Per-subtopic findings — compressed

- 🟢 **Hugging Face** — the distribution hub: Hub + model cards + community quant re-uploads + `hf download` (renamed from `huggingface-cli download`). `safetensors` (trained precision, mmap, what vLLM/transformers/AWQ/GPTQ consume) vs GGUF (single self-describing file, llama.cpp/Ollama/LM Studio; base labs almost never publish GGUF — the community converts). Quant uploaders: **bartowski, unsloth, mradermacher, lmstudio-community, ggml-org**. **HF Open LLM Leaderboard retired March 2025** (benchmarks saturated); no official successor — people now track **LMArena** (human Elo), **Artificial Analysis** (Intelligence Index + throughput/price), and task benchmarks (SWE-bench Verified/Pro, Terminal-Bench, Aider polyglot). Ollama can pull HF GGUF directly (`ollama run hf.co/user/repo:quant`); its own registry lags releases by days–weeks and sometimes ships a bad quant/template. Uploader quality ranking is 🟠 (one community KL-div benchmark).
- 🟡 **Model landscape by hardware class** — mapped to the chapter's tiers:
  - **8–16 GB VRAM:** Qwen2.5-Coder-7B/14B (Apache 2.0, FIM, 128K); Gemma 3/4 12B (vision); **Devstral Small** 24B (Apache 2.0, agent-tuned, **53.6% SWE-V** on OpenHands scaffold — 🟢). Autocomplete tier.
  - **24–32 GB VRAM:** Qwen2.5-Coder-32B (**69.6% SWE-V**, ~20 GB at Q4_K_M — 🟢); **Qwen3-Coder-30B-A3B** (MoE 30.5B/3.3B active, Apache 2.0, 51.6% SWE-V — 🟢); **gpt-oss-20b** (OpenAI, Apache 2.0, MoE 21B/3.6B active, ships MXFP4 → ~16 GB — 🟢); Gemma 4 26B-A4B MoE.
  - **64–128 GB unified memory:** **gpt-oss-120b** (MoE 117B/5.1B active, MXFP4 → ~80 GB, ~62% SWE-V — 🟢 card / 🟡 score); **GLM-4.5-Air** (MoE 106B/12B active, MIT, has MTP layers — 🟢); Qwen3-Next-80B-A3B (~3B active, hybrid, 🟢); Llama 3.3 70B dense (slower — all params move per token).
  - **128 GB+ / multi-GPU / datacenter:** DeepSeek-V3/V3.1/V3.2 (MoE 671B/37B active, MIT — 🟢); **DeepSeek-V4-Pro** (MoE ~1.6T/49B active, **80.6% SWE-V**, MIT — 🟡, 2026); Qwen3-Coder-480B-A35B (Apache 2.0, "~Claude Sonnet 4" — 🟢); GLM-4.6 (357B, MIT — 🟢) / GLM-5.x (~753B/~40B active, MIT, GLM-5.2 Terminal-Bench 2.1 = 81.0 — 🟡, 2026); Kimi K2 (1T/32B active, Modified MIT — 🟢) — **but K2.5/K2.6/K2.7/K3 are proprietary / release-restricted, effectively API-only** (🟡); MiniMax-M2 (MoE 230B/10B active, MIT, SWE-V 69.4% — 🟢).
  - Usage scenarios: FIM autocomplete (1–14B dense / ~3B MoE) → chat assistant (14–32B) → autonomous agent (needs agent-post-trained model, ~30B active-or-dense floor before loops drift).
- 🟢 **Quantization** — weight quant stores params in <16 bits, dequantizes per-block on the fly; cuts memory ~linearly and usually *speeds up* decode (memory-bandwidth bound). Formula: `weights_bytes ≈ params × bpw / 8`, plus KV cache + ~0.3–2 GB compute buffers + headroom (~10–20%). Worked: Qwen2.5-Coder-32B at Q4_K_M ≈ 19.7 GB, Q5_K_M ≈ 22.3 GB, Q8_0 ≈ 34.5 GB.
  - **GGUF families:** legacy (Q4_0…Q8_0); **K-quants** Q2_K–Q6_K with _S/_M/_L mixes (PR #1684, spends more bits on high-impact tensors) — nominal bpw Q4_K 4.5 / Q5_K 5.5 / Q6_K 6.56; **i-quants** IQ1–IQ4 (codebook, ≤3 bpw, need an importance matrix or they collapse); **imatrix** calibration; **Unsloth "Dynamic" 2.0/3.0** per-layer recipes.
  - **GPU-native (safetensors):** GPTQ, **AWQ** (protects ~1% salient channels — de-facto 4-bit GPU-serving standard), EXL2/EXL3 (ExLlama, NVIDIA-only, mixed bpw), bitsandbytes **NF4** (QLoRA paper, Dettmers), **FP8** (native Hopper/Blackwell, ≈BF16), **FP4/MXFP4** (native Blackwell; gpt-oss ships in it).
  - **Quality consensus:** KL-divergence vs FP16 is the preferred proxy. ≥4-bit ≈ near-lossless; ~3-bit noticeable but usable; <3-bit degrades fast on dense (MoE tolerates low bits better). **Coding is quant-sensitive** — stay ≥ Q5_K_M for a coding model if VRAM allows; prefer a smaller model at higher precision over a big model at 2-bit.
  - Engine→format: llama.cpp/Ollama/LM Studio = GGUF only; vLLM/SGLang = AWQ/GPTQ/FP8/compressed-tensors (+ experimental GGUF); ExLlama = EXL2/3; LM Studio MLX = MLX quants.
  - 🟠 **Two prior-note claims flagged:** "llama.cpp extreme quant uses ~35% less VRAM" is **misleading** (4-bit vs FP16 is ~65–70% less); "2-bit GLM retains ~82% accuracy" is a weakly-sourced vendor-style claim.
- 🟢/🟡 **Multi-Token Prediction (MTP)** — extra lightweight heads predict t+2, t+3… in one forward pass. Two uses: (1) **training signal** — densifies loss, improves scores even if heads discarded at inference (DeepSeek-V3, §2.2 — 🟢); (2) **inference-time self-speculative decoding** — the head drafts k tokens, main model verifies in one batch, **no separate draft model to load**. Family: draft-model / Medusa / EAGLE / Lookahead; MTP heads trained with the base ≈ built-in EAGLE. Speedups: DeepSeek-V3 **~1.8× at 80–90% 2nd-token acceptance** (🟢); llama.cpp added MTP in **PR #22673 (~May 2026)**, community reports ~1.7× (e.g. 38→65 tok/s on a 3090) — 🟡. Only models pre-trained with MTP heads benefit (DeepSeek-V3/V4, Qwen3-Next/3.5+, GLM-4.5-Air/5.x, Gemma 4 26B-A4B); Llama 3 / Mistral / older Gemma do not. **Thinnest subtopic** — little independent primary measurement outside DeepSeek's own report.
- 🟢/🟠 **Multimodal models** — llama.cpp rewrote vision from `llava.cpp`/`clip.cpp` into **`libmtmd`** (image + audio); load the LM GGUF **plus an `mmproj-*.gguf`** (vision encoder + projector). Supported: LLaVA, Qwen2-VL/2.5-VL/3-VL, Gemma 3/4 vision, MiniCPM-V, SmolVLM, Ultravox (audio). LM Studio uses `mlx-vlm` on Apple Silicon. **Keep the vision encoder at FP16/8-bit** (4-bit visibly degrades). Overhead: `mmproj` few-hundred-MB–1.3 GB + ~2 GB compute buffers + images expand to hundreds–thousands of context tokens (Gemma 4: 70–1120 tokens/image). One community measurement: 1.3 GB mmproj cut usable context ~36K→~20K on a 31B model at 24 GB (🟠 single anecdote). Agentic-coding relevance: agent reads UI screenshots, mockups, diagrams, error states — but a text-only coder is still preferred for pure code (vision tower costs VRAM + context).
- 🟢 **Mixture-of-Experts (MoE)** — each FFN → N expert FFNs + router picking top-k (k≪N); attention stays dense. Mixtral 8×7B (47B total / ~13B active) set the template; **DeepSeekMoE** added fine-grained expert segmentation + shared-expert isolation (now near-universal). **The key local-inference point:** *you pay memory for ALL params but bandwidth/compute for only the ACTIVE ones.* Since decode is bandwidth-bound, decode speed ∝ active bytes, but the model only fits if total bytes ≤ RAM/VRAM. → **MoE shines on large slow memory** (Apple unified, Strix Halo, DGX Spark, CPU+DDR5): a 235B/22B-active model on a 128 GB Mac streams like a 22B dense but knows far more. Qwen3-Coder-30B-A3B (~3.3B active) vs dense 30B: same ~19 GB footprint, MoE decodes several× faster, but a 3B-active MoE isn't as capable as a good dense 30B (trades quality-per-param for quality-per-FLOP). On a bandwidth-rich single GPU the advantage narrows (a dense model already fits fast). **Expert offloading:** llama.cpp `--n-cpu-moe N` (keep attention/KV/router/shared experts on GPU, push routed-expert FFNs to CPU RAM), `-ot` regex tensor override; **KTransformers** (SOSP'25) runs 671B MoE on one 24 GB GPU + RAM (4.6–19.7× prefill, 1.25–4.1× decode vs prior offload); `ik_llama.cpp` fork.
