Sourcing-confidence convention used throughout (matches `notes/2026-08-18-1-sw-factories-langchain-loop-engineering-deep-research/`):

- 🟡 **corroborated-secondary** — consistent across multiple independent write-ups, not the primary actor's own words.
- 🟠 **single-source** — one write-up only, not independently corroborated.

## 1. KV cache memory-footprint formula and example numbers

The formula in `basics.md` — `2 × Layers × Heads × Head Dimension × Precision(Bytes) × Tokens` — is the standard textbook KV-cache-size formula (the leading `2` accounts for storing both a Key and a Value vector per token). This is a derived arithmetic identity, not a claim needing external corroboration in itself; it is consistent with how the vLLM paper and every serving-engine writeup describe KV cache growth. 🟢 well-established/derivable, not attributable to a single source.

**Llama 3 8B architecture parameters.** Multiple independent technical write-ups agree on the same numbers `basics.md` uses: 32 transformer layers, hidden size 4,096, 32 query attention heads with head dimension 128, and 8 KV heads via Grouped-Query Attention (i.e. a 4:1 query-to-KV-head grouping ratio) — see [emergentmind's Llama 3 8B overview](https://www.emergentmind.com/topics/llama-3-8b), [Local AI Master's spec page](https://localaimaster.com/models/llama-3-8b), and [apxml's spec/VRAM page](https://apxml.com/models/llama-3-8b). 🟡 corroborated-secondary — these are independent technical summaries, not Meta's own published config file; a direct fetch of Meta's gated `config.json` on Hugging Face (`meta-llama/Meta-Llama-3-8B`) returned HTTP 401 (gated repo) in this pass, so the primary artifact itself was not directly read, but the figures are the same, widely-known, and uncontested numbers across every independent source checked.

**Arithmetic check (independently recomputed, not just copied from the note):**
- Per token: 2 × 32 layers × 8 KV heads × 128 head-dim × 2 bytes (FP16) = 131,072 bytes = **131 KB** (using decimal KB; 128 KiB in binary units). Matches `basics.md` exactly.
- At 8,000 tokens: 131,072 × 8,000 = 1,048,576,000 bytes ≈ **1.049 GB** ≈ the chapter's "≈1.05 GB". Confirmed.
- At 128,000 tokens: 131,072 × 128,000 = 16,777,216,000 bytes ≈ **16.78 GB** ≈ the chapter's "≈16.8 GB". Confirmed.

**Verdict: arithmetically verified independently, and the underlying Llama 3 8B parameters are consistently corroborated across secondary sources.** No primary Meta document was directly readable in this pass (gated), but nothing found contradicts the figures.

## 2. Cache-shrinking techniques' quantitative claims

**Grouped-Query Attention (GQA) — "4-8x" cache shrink, minor quality loss.** The GQA cache reduction is a direct mechanical consequence of the sharing factor: cache size shrinks by exactly `H/G` (query heads ÷ KV-head groups), so claiming "4-8x" describes a *typical chosen grouping ratio*, not an independent empirical measurement — e.g. Llama 3 8B itself uses a 4:1 ratio (32 query heads / 8 KV heads). This is confirmed directly against the primary source, [Ainslie et al., "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints" (arXiv:2305.13245)](https://arxiv.org/abs/2305.13245) 🟢: the paper reports that **uptrained GQA-8 on T5-XXL loses under 1% quality versus full multi-head attention (MHA)**, while multi-query attention (MQA, the extreme 1-KV-head case) loses 2-3%, and that converting an existing MHA checkpoint to GQA via mean-pooling K/V heads plus brief fine-tuning costs only about **5% of the original pre-training compute** to recover most of the lost quality. This directly corroborates `basics.md`'s claim that "model quality drops only slightly" under GQA. 🟢 primary.

**KV-cache quantization (INT8/INT4, FP8/FP4) — "2-4x with minimal accuracy loss".** The 2x (INT8/FP8) and 4x (INT4/FP4) memory-reduction multipliers are the direct arithmetic consequence of halving or quartering the per-value byte width from FP16 — not independently disputed. The "minimal accuracy loss" framing is corroborated at the specific NVFP4 level: NVIDIA reports **NVFP4 KV cache cutting footprint by up to ~50% versus FP8, at under 1% accuracy loss**, per synthesis of NVIDIA's own [NVFP4 documentation](https://ai-infrastructure.net/nvfp4-quantization/) and [TensorRT-LLM quantization docs](https://nvidia.github.io/TensorRT-LLM/1.2.0rc5/features/quantization.html) 🟡 corroborated-secondary (NVIDIA-sourced content relayed via independent technical write-ups, not a direct primary fetch of NVIDIA's own page in this pass).

**FP4/FP8 mapping natively onto NVIDIA Blackwell tensor cores.** Directly confirmed against NVIDIA's own documentation: [NVIDIA's Transformer Engine user guide](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/examples/fp8_primer.html) and [NVIDIA's Blackwell architecture page](https://www.nvidia.com/en-us/data-center/technologies/blackwell-architecture/) describe Blackwell's 5th-generation Tensor Core as the **first NVIDIA architecture to natively support FP4 (and FP6) formats**, alongside a "second-generation Transformer Engine" with native FP8 support and new micro-tensor-scaled formats (MXFP8, NVFP4). NVIDIA states Blackwell's FP4 tensor-core throughput is roughly double FP8's on the same hardware. 🟢 primary. This directly corroborates the chapter's specific claim about Blackwell FP4/FP8 native tensor-core support.

**Streaming/sliding-window attention.** Not a numerically-checkable claim in the chapter (no percentage attached) — the general mechanism (capping cache size by dropping tokens outside a moving window, e.g. Mistral's approach) is uncontroversial and well-established; no red flags found.

**Verdict: strongly corroborated overall**, with the GQA and Blackwell claims directly primary-sourced, and quantization's "2-4x" being a straightforward unit-width arithmetic fact rather than an empirical claim needing its own citation.

## 3. PagedAttention / vLLM claims

This is the subtopic where the original note's sourcing was weakest — it cited only a milvus.io blog post — and where independent verification against the actual paper paid off best. The primary source, [Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention" (SOSP '23, arXiv:2309.06180)](https://arxiv.org/abs/2309.06180), was fetched and read directly (PDF, first three pages) for this pass. 🟢 primary, directly read, not just search-synthesized.

**"Traditional serving wastes 60-80% of GPU memory to fragmentation."** The paper's own Figure 2 ("Average percentage of memory wastes in different LLM serving systems") reports that in the existing systems profiled (Orca in its Max, Pow2, and Oracle allocation variants), **only 20.4%-38.2% of KV cache memory is actually used to store real token states** — i.e., **61.8%-79.6% is wasted** to a combination of internal fragmentation, external fragmentation, and reservation overhead. The paper's own text states this explicitly: *"our profiling results in Fig. 2 show that only 20.4% - 38.2% of the KV cache memory is used to store the actual token states in the existing systems."* This is an almost exact match for `basics.md`'s "60-80%" figure. 🟢 primary, confirmed to the specific numbers.

**"PagedAttention reduces waste to under 4%."** The same Figure 2 shows vLLM achieving **96.3% token-state utilization**, i.e. **3.7% waste** — matching the chapter's "under 4%" claim almost exactly. 🟢 primary, confirmed.

**"2-4x higher batching throughput."** Directly quoted from the paper's own abstract: *"vLLM improves the throughput of popular LLMs by 2-4× with the same level of latency compared to the state-of-the-art systems, such as FasterTransformer and Orca."* 🟢 primary, exact match, no rounding needed.

**Copy-on-write block sharing.** Confirmed in the paper's introduction/abstract, which describes vLLM as achieving "flexible sharing of KV cache within and across requests" — the paper's Section 4 (not re-read in full in this pass, but consistent with all secondary descriptions, e.g. [vLLM's own PagedAttention design docs](https://docs.vllm.ai/en/latest/design/paged_attention/)) describes this as copy-on-write at the block-table level, matching the chapter's description. 🟢 primary for the mechanism's existence; the specific "copy-on-write" terminology is standard across vLLM's own docs and the paper.

**16-tokens-per-block example.** Not independently re-verified against the paper's specific default in this pass, but this is vLLM's well-known default block size, consistent across vLLM's own documentation.

**Verdict: this subtopic is now the single best-corroborated section in the whole chapter** — every specific number (60-80% waste, under-4% residual waste, 2-4x throughput) traces to an exact figure or an exact quote in the primary paper itself, not merely "the right order of magnitude." The original note's reliance on a milvus.io blog as its only citation was an unnecessary weak link — the primary paper backs the same numbers directly.

## 4. Anthropic prompt caching mechanics and pricing

Checked directly against Anthropic's own current documentation: [Claude Platform Docs — Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) and the Claude Code-specific page, [code.claude.com/docs/en/prompt-caching](https://code.claude.com/docs/en/prompt-caching), both fetched directly in this pass. 🟢 primary.

**Strict prefix matching, 100% identical from character 0.** Directly confirmed. The Claude Code docs state: *"The API caches by matching the start of each request, called the prefix, against content it recently processed. ... The match is exact, so a change anywhere in the prefix recomputes everything after it. There is no per-file or per-segment caching."* The platform docs likewise describe cache hits as requiring "100% identical prompt segments, including all text and images up to and including the block marked with cache control." 🟢 primary, exact match to the chapter's wording.

**Cache hits cost "roughly 10% of the standard input-token rate."** Directly confirmed at the exact figure. The Claude Code docs' cache-performance section describes `cache_read_input_tokens` as "billed at roughly 10% of the standard input rate," and the Platform docs pricing table states cache read tokens are priced at "0.1 times the base input token price" (a 90% discount) — e.g. for a model priced at $5/MTok input, cache reads are $0.50/MTok. 🟢 primary, exact confirmation of the "roughly 10%" figure — this is not an approximation invented by the Gemini chat, it is Anthropic's own stated rate.

**Cache write pricing** (relevant context not originally in the chapter but useful): a 5-minute-TTL cache write costs 1.25x the base input rate; a 1-hour-TTL write costs 2x. This nuance doesn't contradict anything in `basics.md`, which doesn't discuss write costs, but is worth knowing if the chapter is later expanded.

**Verdict: fully corroborated against Anthropic's own current, primary documentation** — both the strict-matching mechanics and the specific "10%"/90%-discount figure are exactly right, not rounded approximations of some other number.

## 5. Claude Code-specific cache behavior claims

This subtopic also resolved unusually well: Anthropic operates a dedicated, current, and highly detailed official documentation page — [code.claude.com/docs/en/prompt-caching](https://code.claude.com/docs/en/prompt-caching) — plus an engineering blog post, ["Lessons from building Claude Code: Prompt caching is everything"](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything). Both were fetched directly. 🟢 primary. This is a stronger sourcing situation than the original note had access to (it cited `code.claude.com/docs/en/prompt-caching` too, but the version fetched now is Anthropic's *current* page, and it is considerably more detailed/nuanced than the chapter's summary).

**Layered payload (system/tools → CLAUDE.md/project rules → history).** Confirmed. The current docs describe exactly this three-layer structure: "System prompt" (core instructions, tool definitions, output style) → "Project context" (CLAUDE.md, auto memory, unscoped rules) → "Conversation" (messages, responses, tool results), explicitly ordered so "content that rarely changes between turns comes first." 🟢 primary, matches the chapter closely.

**File-edit invalidation via `<system-reminder>` appends.** Confirmed almost verbatim. Anthropic's own blog post states: *"we add a `<system-reminder>` tag in the next user message or tool result with the updated information for the model, which helps preserve the cache."* The current docs page repeats this: editing a file Claude previously read "does not retroactively change the earlier read in history. Instead, Claude Code appends a `<system-reminder>` noting the file changed, and Claude re-reads it if needed." 🟢 primary, essentially a direct quote match to the chapter's phrasing.

**Cache-safe `/compact` (forking pattern preserving the prefix).** Confirmed, but the primary source reveals an important nuance the chapter's phrasing slightly glosses over. It is correct that *the summarization step itself* is cache-safe: the docs state that to produce the compaction summary, Claude Code "sends a separate request with the same system prompt, tools, and history as your conversation, plus a summarization instruction appended as a final user message. While the cache is warm, that request reads your prefix from the cache, so a mid-session `/compact` costs a fraction of what the context size suggests." However, compaction *does* invalidate the conversation layer going forward: "By design, this invalidates the conversation layer, since the next request has a new, shorter history that doesn't share a prefix with the old one." So: the compaction *request itself* is a cache hit (matching the chapter), but the chapter's framing ("so the compaction step itself is a cache hit") could be read as implying `/compact` is fully cache-neutral overall, when in fact the *resulting* shorter conversation must build a fresh cache on the next turn. 🟢 primary — confirmed with a nuance worth tightening in the chapter text.

**Delayed application of `/config` changes mid-session.** Confirmed, and more precisely specified than the chapter's general phrasing. The docs specifically confirm this for CLAUDE.md and output style: editing CLAUDE.md mid-session "does not invalidate the cache, but the edit also doesn't apply. Claude keeps working with the version that was loaded at session start. The new content loads on the next `/clear`, `/compact`, or restart" — and the same for output style changed via `/config`. 🟢 primary, confirmed.

**"What still nukes the cache": model switch, MCP connect/disconnect, extended-thinking-budget change.** Partially confirmed, but the MCP claim is now **outdated relative to current Claude Code behavior**, and "extended thinking budget" appears to have been superseded in terminology:
- **Model switching**: confirmed exactly — "each model has its own cache. Switching ... means the next request reads the entire conversation history with no cache hits." 🟢
- **MCP server connect/disconnect**: the *current* docs make this conditional, not absolute. Whether it invalidates the cache "depends on whether its tools are deferred by tool search ... or loaded into the prefix": with **deferred tools (the default on supported models)**, "a server connecting, disconnecting, or changing its tool list only appends new content and doesn't disturb anything already cached" — the cache only breaks when tools are loaded directly into the prefix, which now happens only in specific fallback cases (older models without tool search, certain gateway configurations, or a server explicitly marked to always load). So the chapter's blanket claim that MCP connect/disconnect "force a full cache miss" is **no longer accurate as a universal statement** under current Claude Code versions — it's conditional on tool-search/deferred-loading support. 🟡 corroborated-secondary at best for the blanket version; 🟢 primary for the more nuanced, conditional current behavior.
- **"Extended thinking budget"**: the current docs do not use this exact term. The closest current equivalent is **"effort level"** (`/effort`), which the docs confirm does force a full cache miss ("the cache is keyed by effort level as well as model, so switching ... means the next request reads the entire conversation history with no cache hits"). This suggests either a terminology shift since the note was written, or a conflation of an older "thinking budget" concept with the current "effort level" setting — the underlying behavior (changing it mid-session busts the cache) is corroborated, but the specific term "extended thinking budget" could not be matched verbatim in current documentation. 🟡 corroborated-secondary (behavior matches; term may be dated).

**Bearing of the Open-Claw/Hermes Agent question on this section's generalized claims:** `basics.md`'s "How agentic harnesses structure prompts around it" section generalizes patterns (explicit cache boundaries, progressive/on-demand tool disclosure, mid-session memory freezing, append-only history) to "agentic harnesses" broadly, without naming Open-Claw or Hermes Agent. Investigating those two products directly (see boxed verdict below) found that **both are real, existing products** — not hallucinations — but neither is actually a "coding harness" in the Claude-Code/Cursor/Aider sense; both are general-purpose personal-assistant agents (messaging-platform-first: WhatsApp/Telegram/Discord/Signal for OpenClaw, a similar multi-platform personal-agent design for Hermes Agent). Their real documentation does confirm the *general shape* of the patterns `basics.md` generalizes — OpenClaw's actual docs describe a "stable prefix"/"volatile suffix" cache boundary (a real, if less elaborate, version of "explicit cache boundaries"), and OpenClaw's own GitHub issues/architecture writeups confirm a genuine progressive/lazy skill-disclosure design. So the *general architectural pattern* `basics.md` describes is independently corroborated (it's also exactly how Claude Code itself works, per the primary sources above) — but the specific numbers attached to Open-Claw/Hermes in the original note (a fixed "25 sections," a "9-layer prompt composition," "progressive 3-tier skill disclosure" cutting cost by "up to 75%") could **not** be corroborated on either product's actual official documentation and read as invented specifics layered onto real product names. Since `basics.md` itself doesn't repeat those specific fabricated numbers — it only generalizes the qualitative pattern — the chapter's own text is not directly contaminated by the fabricated figures, but the *pattern itself* should be understood as "well-corroborated because it matches Claude Code's own documented behavior," not because Open-Claw/Hermes prove it as independent data points the way the original note implied.

**Verdict: strongly corroborated for the core Claude Code claims** (layered payload, system-reminder invalidation, cache-safe compaction request, delayed `/config` application, model-switch cache miss) against Anthropic's own current, primary documentation — with two specific corrections needed: (1) the MCP-server claim is now conditional/outdated as a blanket statement given deferred tool-search loading, and (2) "extended thinking budget" is not current terminology (current equivalent: "effort level"), though the underlying mid-session-change-busts-cache behavior is confirmed.

## 6. Context/loop-engineering savings percentages

This subtopic has the weakest sourcing of the six, consistent with the assignment's expectation — the original note's ~20 blog citations (tessl.io, omnithium.ai, fast.io, morphllm.com, etc.) are exactly the kind of SEO-blog echo chamber that tends to repeat unsourced round numbers. Independent search in this pass found a mix of genuinely corroborating academic/industry sources and numbers that do not match.

**"Communication tax" (code blocks passed back and forth) accounting for "up to ~60%" of an unoptimized run's total token spend.** This is the single figure in this subtopic that corroborated unusually well, via an academic source rather than a blog: the arXiv paper ["Tokenomics: Quantifying Where Tokens Are Used in Agentic Software Engineering" (arXiv:2601.14470)](https://arxiv.org/html/2601.14470v1) reports that **input tokens make up 53.9% of total token usage on average**, explicitly calling this a **"communication tax"** and stating "the majority of the tokens are spent on communicating context rather than generating novel output." More specifically, it finds the **Code Review phase alone consumes 59.4% of all tokens** in a multi-agent pipeline, characterizing this as the "Cost of Conversation": *"agents iteratively pass the full code context back and forth to refine it."* The 59.4% figure is a very close match to the chapter's "up to ~60%." 🟠 single-source (one academic paper, not cross-corroborated by a second independent source) but a strikingly close numeric match to a specific, checkable figure — stronger than a typical single-source finding because it's a direct measurement rather than a repeated blog assertion.

**Loop engineering cutting token usage/cost by "60-80%".** Corroborated only as a compound/combined figure, not as a single technique's isolated effect: one industry source states that combining prompt caching (~90% discount on repeated prefixes) with other loop-engineering practices drops "total loop costs 60 to 80 percent" — consistent with, but not independently isolating, the chapter's claim. 🟠 single-source for the specific combined range; the underlying components (prompt caching's ~90% cache-hit discount) are separately confirmed in section 4 above.

**Table row: "Prompt caching → 60-90% savings."** The upper bound (90%) is directly and exactly confirmed by Anthropic's own pricing (section 4: cache reads cost 10% of base rate). The lower bound (60%) is not an official Anthropic figure but is plausible as a blended session-level savings rate depending on cache-hit ratio (i.e., a session with a lower hit rate saves less than the full 90% per-token discount). 🟡 corroborated-secondary for the range as a whole; 🟢 primary for the 90% ceiling specifically.

**Table row: "Just-in-time context → 50-70% savings."** Found a genuine matching case study: [TrueFoundry's JIT-context piece](https://www.truefoundry.com/blog/jit-context-just-in-time-context-agents) reports a concrete matplotlib-repository test case achieving **57% token savings (4.0M → 1.7M tokens)** from just-in-time context loading — squarely inside the chapter's claimed 50-70% range. 🟠 single-source (one case study), but a genuine, specific, matching data point rather than an unsupported assertion. Other sources found report different, generally lower figures for related-but-not-identical techniques (e.g. a "Focus" context-compression method reporting 22.7% reduction, and one study finding full-context vs. optimized-context agents differing by 2.68x on a 50-task benchmark, which is a larger gap than 50-70% savings would imply) — so the range is plausible and has at least one direct match, but is not uniformly confirmed across all sources checked.

**Table row: "State compaction → 40-60% savings."** **Not well corroborated** — most sources found report figures below this range: production-agent write-ups describe compaction strategies delivering **20-30% cost reduction** typically, and one academic "SupervisorAgent" pattern reports **29.68% average token reduction**. Anthropic's own [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) engineering post — fetched directly in this pass 🟢 — describes compaction (summarizing a conversation nearing its context limit and reinitiating with the summary) as a real, recommended technique, but **gives no percentage figures at all** for its savings. **Verdict: the mechanism is real and Anthropic-endorsed, but the specific 40-60% range could not be corroborated — independently found figures cluster lower, around 20-30%.**

**Table row: "Subagent splitting → up to 15x savings."** This is the most important finding in this subtopic, and it is a likely inversion of a real, well-known number rather than an invented one. Anthropic's own engineering post, ["How we built our multi-agent research system"](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) (and independent write-ups discussing it, e.g. [Simon Willison's summary](https://simonwillison.net/2025/Jun/14/multi-agent-research-system/)), states that **multi-agent systems use approximately 15x more tokens than single chat interactions** — presented by Anthropic as a *cost* to be weighed against task value ("multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance"), not as a savings figure. 🟢 primary for the "~15x" number itself. `basics.md`'s table row frames "up to 15x" as the *savings* subagent delegation produces ("Restrict deep chatter to isolated, narrow code scopes" → "up to 15x" in the "Typical savings" column) — this appears to take a real, well-known, primary-sourced number and **flip its meaning**: the well-established "15x" describes multi-agent systems' token *overhead* relative to a single agent, not a reduction that subagent delegation achieves. It is possible the note's chat conflated "isolating a subagent's own internal chatter so it doesn't pollute the orchestrator's context" (a real, separately-confirmed benefit — Anthropic's own context-engineering post confirms subagents return only "a condensed, distilled summary of its work, often 1,000-2,000 tokens" back to the parent) with the unrelated "15x" figure that actually describes something else entirely (total multi-agent token cost vs. single-agent cost). **Verdict: the "15x" figure is real and primary-sourced, but as used in the chapter's table it very likely misattributes what that number measures — this specific table cell should be treated as unsupported/likely incorrect as stated, not merely "weakly corroborated."**

**Verdict, subtopic 6 overall:** the "communication tax ~60%" claim corroborated unusually well against an academic source; the "prompt caching 60-90%" and "JIT context 50-70%" rows have genuine (if single-source) supporting data points; the "state compaction 40-60%" row is **not corroborated** (independent figures run lower, 20-30%); and the "subagent splitting up to 15x" row is the chapter's weakest specific claim — it very likely repurposes a real Anthropic figure that means the opposite of what the table implies.

## Open-Claw and Hermes Agent: existence check (bears on sections 5 and the chapter's general "how harnesses structure prompts" claims)

Both names were searched directly, independent of the original note's framing, to determine whether they are real products or hallucinated.

**"Open-Claw" / OpenClaw is a real, very prominent open-source project** — though not under the note's exact framing. Per [Wikipedia's OpenClaw entry](https://en.wikipedia.org/wiki/OpenClaw), [its GitHub repo](https://github.com/openclaw/openclaw), and multiple independent write-ups, it was created by Austrian developer Peter Steinberger, first published in November 2025 under the name "Warelay," then renamed successively (CLAWDIS → Clawdbot → Moltbot, after an Anthropic trademark complaint over the "Claw"/"Claude"-adjacent branding → OpenClaw as of January 30, 2026). It grew explosively — reportedly surpassing 250,000 GitHub stars by March 2026, among the fastest-growing repositories ever. It is fundamentally a **personal AI assistant reached through messaging platforms** (WhatsApp, Telegram, Signal, Discord, Slack, iMessage, etc.), with local execution and a skills-directory system, not a dedicated coding harness like Claude Code/Cursor/Aider — though its skills system can include coding-related skills. Its real documentation (`docs.openclaw.ai`) does describe a genuine "stable prefix"/"volatile suffix" cache-boundary design and a genuine progressive/lazy skill-disclosure mechanism (confirmed via a real [GitHub issue on progressive disclosure](https://github.com/openclaw/openclaw/issues/39945) and independent architecture write-ups) — real patterns, but simpler and less elaborately specified than the original note's invented details (a fixed "25 sections," alphabetized tool ordering, named `cacheRead`/`cacheWrite` metadata fields).

**"Hermes Agent" is also a real product**, released by Nous Research in February 2026, per [Nous Research's own site](https://hermes-agent.nousresearch.com/), [its GitHub repo](https://github.com/nousresearch/hermes-agent), and an [NVIDIA blog post](https://blogs.nvidia.com/blog/rtx-ai-garage-hermes-agent-dgx-spark/) covering it running on RTX/DGX Spark hardware. Like OpenClaw, it is a **general-purpose, self-improving personal AI assistant** (persistent memory, self-created skills, multi-platform messaging gateway) rather than a coding-specific harness. A direct fetch of its own marketing/docs page found **no mention of a "9-layer prompt composition architecture," "progressive 3-tier skill disclosure," or "up to 75% cost reduction"** — those specific figures were only found in secondary blog write-ups (e.g. `fp8.co`, `arapaholabs.com`) discussing Hermes' caching behavior, not in Hermes/Nous Research's own primary documentation checked in this pass.

**Verdict: both products are real** (not hallucinated), which is a partial correction to the "red flag" framing this task started from — but the original note's specific attribution of them as **coding harnesses**, and its specific numeric architectural claims (25 sections, 9 layers, 75% reduction, 3-tier disclosure), go beyond what their own primary documentation supports. Since `basics.md` itself never names Open-Claw or Hermes Agent and only generalizes the qualitative pattern (explicit cache boundaries, progressive disclosure, mid-session freezing, append-only history), the chapter is not directly contaminated by the specific fabricated numbers — but that generalization is best understood as corroborated by **Claude Code's own primary documentation** (section 5 above), not by Open-Claw or Hermes Agent, whose real documentation only loosely and partially matches the pattern.
