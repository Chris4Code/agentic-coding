> **Headline:** contrary to what the earlier Qwen3.x pass feared, **Qwen3.8 is well-attested by first-party material.** The `QwenLM/Qwen3.8` GitHub repo, both HF model cards (`Qwen/Qwen3.8-27B`, `Qwen/Qwen3.8-2.4T-A95B`), their `config.json` and `LICENSE` files, and the official FP8 repos are all reachable and internally consistent. Only the Qwen blog itself (`qwen.ai/blog?id=qwen3.8`) is a JS SPA that couldn't be scraped — but the repo and cards mirror it. The one genuinely soft area is real-world consumer-GPU tokens/sec (community posts only).

## Per-subtopic findings — compressed

- 🟢 **Release and lineage.** Qwen3.8 is an **August 2026 point release within the Qwen3.5 series lineage** (3.5 → 3.6 → 3.8), published by the Qwen Team / Alibaba, "built on the architectural foundation of Qwen3.5." Dates: **Qwen3.8-2.4T-A95B** on 2026-08-12, **Qwen3.8-27B** on 2026-08-14. **Qwen3.7 has no open weights** — "Qwen3.7-Plus/-Max" appear only as hosted-API baseline columns in Qwen3.8's comparison tables. **There is no `Qwen3.8-Coder` variant** — the `QwenLM/Qwen3-Coder` line (30B-A3B, 480B-A35B) was not bumped to 3.8; coding is pitched as a first-class capability of the general models, and Qwen ships **Qwen Code** (a CLI harness, not a model). No technical report — blog only.
- 🟢 **Variants and architecture.** Two open checkpoints, both native vision-language, both "thinking by default" with an instruct/non-thinking toggle + `reasoning_effort` (`xhigh` default / `medium` / `low`), both MTP-equipped (`mtp_num_hidden_layers: 1`, head bundled in the checkpoint), both **262,144 native context, ~1M via static YaRN**. No separate `-Instruct` / `-Thinking` / `-Base` repos.
  - **Qwen3.8-27B** — **dense** (~27.5–27.8 B params), 64 layers, but **hybrid attention** (`model_type: qwen3_5`, same family as Qwen3-Next): **48 Gated-DeltaNet linear-attention layers + 16 full-attention GQA layers** (24 Q heads / 4 KV heads, head dim 256, partial RoPE). ~27-layer ViT vision encoder. This is the consumer-relevant checkpoint.
  - **Qwen3.8-2.4T-A95B** ("Qwen3.8-Max" open base) — **MoE, 2.4 T total / 95 B active**, 512 experts (10 routed + 1 shared), 92 layers, same hybrid attention. Text-only in the open checkpoint (vision + 1M-default + built-in tools are hosted-only). Ships an official FP8 repo (~2.4 TB). **Datacenter-only — out of scope for consumer tiers.**
- 🟢/🟡 **Coding / agentic benchmarks.** Qwen's first-party tables for Qwen3.8-27B **do not report SWE-bench Verified, Aider polyglot, or classic Terminal-Bench.** They report (all under the **Claude Code harness**, 256K ctx): **SWE-bench Pro 61.7**, in-house **QwenSWEBench 79.0**, **Terminal Bench 2.1 (Terminus) 73.0**, **DeepSWE 1.1 42.2**, **LiveCodeBench v6 90.3**, NL2Repo-Bench 42.3, plus VL-agentic OSWorld-Verified 84.3. Large jump over Qwen3.6-27B on Qwen's own numbers (SWE-bench Pro +8.2, QwenSWEBench +30, OSWorld +20) — treat the *magnitude* of the gap with mild caution since some benchmarks (QwenSWEBench, "refined" SWE-bench Pro) are Qwen-curated. **No apples-to-apples comparison to the chapter's Qwen anchors is possible** (Qwen2.5-Coder-32B 69.6% SWE-bench *Verified*; Qwen3-Coder-30B-A3B 51.6%) — different benchmark, harness, and year. SWE-bench Verified ≈85.6 for Qwen3.8-**Max** (the MoE) is 🟡 secondary-only.
- 🟡/🟢 **Consumer GPUs.** Only **Qwen3.8-27B** is a consumer target. Weight sizes (🟢 arithmetic from `config.json`): BF16 ≈ 55 GB; **Q4_K_M ≈ 16.5 GB**, Q5_K_M ≈ 19 GB, Q6_K ≈ 22.7 GB, Q8_0 ≈ 29 GB, official FP8 ≈ 27.5 GB, NVFP4 ≈ 15–16 GB. **KV cache is small** because of the hybrid architecture — only 16 of 64 layers carry a conventional cache: ~64 KiB/token, so ~2 GiB at 32K context, ~8 GiB at 128K (a conventional 27B would need ~4× that). The 48 Gated-DeltaNet layers keep only a fixed-size recurrent state. Measured total VRAM at Q4_K_M (🟡 Hardware Corner): 32K ctx ≈ 20 GB, 64K ≈ 22 GB, 128K ≈ 26 GB, 256K ≈ 34 GB.
  - **16 GB — no.** Q4_K_M weights alone (~16.5 GB) overflow before any context. Run a ~3B-active MoE instead: **Qwen3-Coder-30B-A3B** (chapter anchor) or **Qwen3.6-35B-A3B**.
  - **24 GB (RTX 3090 / 4090, RX 7900 XTX) — the sweet spot, the tier this model is *for*.** Q4_K_M + up to ~64K context fits ~22 GB. Decode ~35–46 tok/s (🟡 community), ~65 tok/s on a 4090 with the bundled **MTP self-speculative decoding** (no draft model; ~2× throughput; `--speculative-config` in vLLM, merged in llama.cpp ~May 2026). Genuinely usable in a multi-file agent loop.
  - **32 GB (RTX 5090) — yes.** Q4_K_M to ~128K context, or Q6_K / FP8 / NVFP4 (RTX-50xx-native) at moderate context.
  - **Quant floor: Q4_K_M.** Gated-DeltaNet SSM state is disproportionately sensitive to low-bit quantization (🟠 one detailed community thread); generic IQ2/IQ3 recipes degrade it badly and below Q4 tool-calling gets unreliable. Prefer uploaders that special-case the hybrid layers (unsloth Dynamic, `-MTP`-aware quants).
- 🟢/🟡 **Licensing and availability.**
  - **Qwen3.8-27B: Apache 2.0** (🟢 card front-matter), ungated on HF.
  - **Qwen3.8-2.4T-A95B: custom "Qwen3.8-Max License"** (🟢 `LICENSE` file) — permissive (use/modify/host/fine-tune/sell allowed) with two carve-outs: products >100 M MAU or >US$20 M/month must display the model name; a Model-as-a-Service / "AI Work Assistant" business >US$50 M revenue over any 12 months needs a separate license. Unrestrictive for essentially all local/self-hosted developer use.
  - First-party HF repos: `Qwen/Qwen3.8-27B`, `-27B-FP8`, `-2.4T-A95B`, `-2.4T-A95B-FP8`. No first-party GGUF/AWQ/Base. Community quants within ~2 weeks: **unsloth GGUF + NVFP4**, `cyankiwi` AWQ-INT4, `turboderp` exl3, `mlx-community` 4bit, plus many `-MTP` GGUF builds and a ROCm quant.
  - **Ollama:** `ollama.com/library/qwen3.8` live — `qwen3.8:27b`, `qwen3.8:latest` (~17.8 GB Q4 build with vision), `qwen3.8:27b-mlx` (🟡 secondary).
  - **Engine support:** architecture is `qwen3_5` — needs the same loader support Qwen3.5/Qwen3-Next required, not a new one. vLLM and SGLang have **first-party Qwen3.8 recipes**; MLX supports the series. **llama.cpp caveat (🟡):** use an **August-2026-or-later build** — earlier builds produced garbage output from a broken CUDA Gated-DeltaNet path (fixed ~build 10450).

## Named-entity notes

- **Qwen3.7** — real as a hosted-API tier ("Qwen3.7-Plus", "Qwen3.7-Max") but **no open weights**; the open line is 3.5 → 3.6 → 3.8.
- **No `Qwen3.8-Coder`** exists. If the chapter or notes elsewhere imply one, that's wrong.
- Qwen's own comparison tables cite competitor baselines ("Opus 4.6/4.8", "Fable 5", "GPT 5.6 Sol", "Muse Glimmer-30B") — post-cutoff, **not independently verified** in this pass, and only appear as baseline columns; don't propagate them into the chapter.
- Earlier pass's "Qwen3.8 (later)" placeholder is now resolved: **August 2026, two open checkpoints, well-sourced.**

## What this means for `src/local-models.md` (suggestion, not decided)

The `## Models` section is the destination. Proposed edits:

1. **24–32 GB VRAM tier row of the model table** — add **Qwen3.8-27B**: dense 27B with hybrid Gated-DeltaNet + GQA attention (so a small KV cache — long context is cheap), native vision-language, bundled MTP, 262K context, Apache 2.0; ~16.5 GB at Q4_K_M, 24 GB is the target tier, keep quant ≥ Q4_K_M. Note it as the current-generation Qwen dense coding-capable model, with **Qwen3-Coder-30B-A3B still the pick below 24 GB / for CPU offload** (MoE, ~3B active).
2. **The 2026-model `Research Note:`** — Qwen3.8 is a partial exception to that note's "specifics rest on secondary sources" caveat: it *is* first-party-sourced (repo + cards + config + LICENSE). But add the real caveat that applies instead: **its benchmark tables use SWE-bench Pro / QwenSWEBench / Terminal-Bench 2.1 under the Claude Code harness, not SWE-bench Verified**, so its coding scores are not directly comparable to the Qwen2.5-Coder-32B / Qwen3-Coder-30B-A3B numbers in the same table. Also fold in that the Kimi/GLM/DeepSeek 2026 names are separate from Qwen here.
3. **Optional, `### Consumer GPUs` or a new sentence near the VRAM table** — the hybrid-attention "only some layers cache KV" point is a genuine architectural development worth one sentence: newer models (Qwen3-Next, Qwen3.5/3.8) mix linear-attention and full-attention layers, which cuts KV-cache growth several-fold and makes long-context local agent loops affordable on 24 GB. This is mild scope expansion beyond "add Qwen3.8" — flag for the user.
4. **llama.cpp build-version caveat** — a short parenthetical or `Research Note:` that a very new architecture like `qwen3_5` needs a current llama.cpp build (older builds silently mis-run the Gated-DeltaNet path).
5. `hybrid-setups.md` currently lists "Qwen3-Coder-30B-A3B, Devstral, gpt-oss-20b" as the 24–32 GB local coder examples — Qwen3.8-27B could be added there too, but that's outside the "add to local-models.md" request; mention only.
